# Тестовый стенд на Railway: настройка по шагам

Короткая инструкция, когда подписка Railway (тариф Hobby или выше) уже есть. Что такое стенд, демо-аккаунты и проверка на уязвимости — в [staging.md](staging.md); боевой запуск — в [deploy.md](deploy.md).

Что получится:

- окружение `staging` — сайт с вымышленными данными, обновляется после каждого мержа в `main`;
- стенд на каждый PR — своя копия с кодом из ветки PR, обновляется после каждого пуша в PR и удаляется после мержа или закрытия.

## 1. Проект и окружение

1. **Account Settings → Default Region → EU West (Amsterdam)** — данные стенда тоже должны жить в ЕС.
2. **New Project → Empty Project.**
3. Вверху в списке окружений: **+ New Environment → Empty Environment**, имя `staging`. Окружение `production` не трогайте — оно для боевого запуска (deploy.md).

Всё дальше делается в окружении `staging`.

## 2. База

**+ Create → Database → PostgreSQL.** Имя сервиса оставьте `Postgres` — на него ссылаются переменные ниже.

## 3. Приложение

1. **+ Create → GitHub Repo → `SvamiBog/visa_crm`.** Railway попросит доступ к репозиторию — разрешите.
2. В **Settings** сервиса:
   - **Source → Branch:** `main`;
   - **Build → Dockerfile Path:** `/Dockerfile` — без него Railway собирает своим сборщиком (Railpack), а не по `Dockerfile` (deploy.md, шаг 3);
   - **Deploy → Healthcheck Path:** `/api/health`;
   - **Deploy → Restart Policy:** On Failure.

   Стенды PR копируют эти настройки из `staging`, поэтому правьте их здесь, а не в стенде.
3. **Settings → Networking → Generate Domain.**

## 4. Переменные приложения

Сервис приложения → **Variables → RAW Editor**:

```
ENV=staging
DATABASE_URL=${{Postgres.DATABASE_URL}}
VAULT_MASTER_KEY=<ключ>
SECRET_KEY=<серверный ключ>
SEED_DEMO=1
DEMO_PASSWORD=<пароль демо-аккаунтов, от 10 символов>
SMTP_HOST=${{Mailpit.RAILWAY_PRIVATE_DOMAIN}}
SMTP_PORT=1025
SMTP_TLS=none
MAIL_FROM=VisaCRM staging <no-reply@staging.visacrm.test>
```

Ключи — в любом Python 3:

```bash
python3 -c "import base64,os;print(base64.b64encode(os.urandom(32)).decode())"   # VAULT_MASTER_KEY
python3 -c "import secrets;print(secrets.token_urlsafe(48))"                      # SECRET_KEY
```

- Ключи стенда — свои, не такие, как в `production`. Они копируются и в стенды PR. Это допустимо, пока в `staging` только демо-данные: у стенда PR своя пустая база, а ключ расшифровывает только записи базы `staging`.
- Без `SECRET_KEY` от 32 символов стенд не запускается: вне `local` и `test` сайт не работает с пустым или коротким серверным ключом.
- После сохранения запечатайте `DEMO_PASSWORD`: в списке переменных у неё ⋮ → **Seal**. Запечатанное значение приложение `staging` получает как обычно, но Railway не копирует его в стенды PR, и каждый стенд PR придумывает себе свой пароль (шаг 8). Снять печать нельзя, поменять значение можно.
- Остальные переменные не запечатывайте: запечатанные значения не попадают в стенды PR, а им нужны `ENV`, `SEED_DEMO`, оба ключа (`VAULT_MASTER_KEY` и `SECRET_KEY`) и ссылки на базу и Mailpit.
- `DEMO_TOTP_SECRET` здесь не задавайте. Это общий секрет двухфакторного входа всех демо-аккаунтов, и вместе с паролем он даёт вход демо-админом, который может открыть любой кабинет стенда. Двухфакторный вход проверяют, включив его в «Настройках» своего демо-аккаунта (шаг 7).
- Пароль передавайте тестировщикам лично, не в открытых чатах и не в репозитории.
- Хранилище файлов для согласий, договоров и шаблонов: в окружении `staging` создайте бакет `Files` в EU West и добавьте те же пять переменных `S3_*`, что в production (deploy.md, шаг 4 → «Хранилище файлов»). Это ссылки, поэтому каждый стенд PR получает свой пустой бакет, а файлы стенда никогда не попадают в бакет production. Без переменных загрузка файла на стенде отвечает «Хранилище файлов пока не настроено».

## 5. Ловушка писем Mailpit

Все письма стенда (код смены почты, уведомления) попадают сюда, а не на настоящие адреса.

1. **+ Create → Docker Image →** `axllent/mailpit`, имя сервиса строго `Mailpit`.
2. Переменные:
   ```
   MP_SMTP_BIND_ADDR=[::]:1025
   MP_UI_BIND_ADDR=[::]:8025
   MP_UI_AUTH=tester:<пароль для просмотра писем>
   ```
3. **Settings → Networking → Generate Domain**, порт `8025` — по этому адресу открываются письма. Порт 1025 наружу не открывайте.

## 6. Запуск и проверка

1. **Deploy.** При первом старте применятся миграции и создадутся демо-данные (5 визовиков, по 240–375 клиентов) — около 15 секунд. Повторный старт ничего не дублирует.
2. `https://<домен>/api/health?db=1` должен ответить `{"status":"ok","db":"ok"}`. Имя окружения этот адрес не называет.
3. На сайте вверху — оранжевая плашка «Тестовый стенд»: она и показывает, что у стенда `ENV=staging`. Документации API (`/api/docs`) на стендах нет, она только на машине разработчика.

## 7. Вход и код подтверждения

Двухфакторный вход — по желанию для всех: каждый включает и выключает его сам в **«Настройки» → «Двухфакторный вход»**. У демо-аккаунтов он выключен, вход только по паролю.

| Кто | Email |
| --- | --- |
| Админ платформы | `admin@demo.visacrm.test` |
| Визовики | `visa1@demo.visacrm.test` … `visa5@demo.visacrm.test` |
| Сотрудники | `visa1.staff@demo.visacrm.test` … `visa5.staff@…` |

**Пароль.** На `staging` у всех демо-аккаунтов пароль из `DEMO_PASSWORD`. На стенде PR пароль свой, его печатает лог стенда (шаг 8).

**Код, если двухфакторный вход включили сами** — в приложении-аутентификаторе, куда вы добавили аккаунт по QR-коду. Если код не подходит, проверьте, что время на телефоне ставится автоматически.

**Стенд заполняли с `DEMO_TOTP_SECRET`.** Так было до 2026-11: тогда у демо-админа и визовиков двухфакторный вход уже включён. Удалите переменную `DEMO_TOTP_SECRET` и сбросьте стенд (раздел «Сброс стенда»): демо-аккаунты создадутся без кода.

Письма (например, код подтверждения при смене почты) читаются в Mailpit по адресу из шага 5.

## 8. Обновления: после мержа и на каждый PR

**После мержа в `main`** окружение `staging` обновляется само: сервис собран из ветки `main`, Railway выкатывает каждый новый коммит.

**На каждый PR — свой стенд:**

1. **Project Settings → Environments → Enable PR Environments**, базовое окружение — `staging`. **Focused PR Environments** — выключить: с ней Railway поднимает в окружении PR только сервисы, которые PR затрагивает, Mailpit (готовый образ) не поднимается никогда, а приложение, которое ссылается на него в `SMTP_HOST`, час ждёт его в очереди и стартует без писем (выключено 2026-10-17). **Enable Bot PR Environments** — выключить: PR от ботов вроде Dependabot несут чужой код, стенд для них не нужен. PR от людей вне проекта Railway не собирает сам: стенд получают только участники рабочего пространства или приглашённые в проект.
2. Когда открывается PR, Railway создаёт окружение `<проект>-pr-<номер>`: копию `staging` со своей пустой базой, Mailpit и приложением из ветки PR. Переменные копируются из `staging`, кроме запечатанного `DEMO_PASSWORD`. Демо-данные создаются при старте.
3. **Пароль стенда.** Без `DEMO_PASSWORD` стенд придумывает случайный пароль демо-аккаунтов и один раз печатает его в лог: сервис приложения → **Deployments** → первая выкладка → **Deploy Logs**, строка `Demo accounts of this stand sign in with the password …`. Пароль открывает только этот стенд. Передавайте его так же, как пароль `staging`: лично, не в открытых чатах.
4. Каждый пуш в PR пересобирает его стенд; база сохраняется, демо-данные не дублируются, пароль прежний. После сброса базы стенд придумает новый пароль и напечатает его в лог новой выкладки.
5. Адрес — в окружении PR: сервис приложения → **Settings → Networking**. Если адреса нет — **Generate Domain**.
6. После мержа или закрытия PR Railway удаляет его окружение сам.

Пока PR открыт, его стенд работает и стоит денег (приложение, база, Mailpit) — старые PR лучше не держать открытыми.

**Если первая выкладка стенда упала.** 2026-10-26 первые выкладки стендов PR #52–#54 падали. Случай двойной:

- у Railway был сбой сборок в EU West (status.railway.com: «Slow build snapshot uploads in EU West»);
- первая выкладка нового стенда не прочитала тогдашний `railway.json` и собиралась Railpack.

Теперь сборщик задан путём к Dockerfile в настройках `staging` (шаг 3), и стенд получает его при создании. Что проверить:

1. В окружении PR: приложение → **Settings → Build → Dockerfile Path** — `/Dockerfile`. У стендов, созданных до 2026-10-26, пути нет — задайте его вручную.
2. Лог сборки. Если там только `All aboard, next stop: builder v4` или `Build Failed: build daemon returned an error`, это сбой Railway, а не кода: проверьте status.railway.com и после сбоя нажмите **Redeploy** (или запушьте в PR).
3. Сборка прошла, а проверка здоровья — нет («Healthcheck failed»), и в логе выкладки `socket.gaierror: Name or service not known` из `alembic upgrade head`: приложение стартовало раньше, чем поднялась новая база стенда (так упал первый стенд PR #66 28.10.2026). Теперь `start.sh` перед миграциями до 3 минут ждёт базу (`python -m app.cli wait-db`). Если и так не дождался — в окружении PR проверьте, что сервис **Postgres** есть и в статусе Active, затем **Redeploy** приложения.
4. В логе выкладки `Demo data refused: …`, и стенд не стартует. `ENV is not set` — у стенда нет переменной `ENV`: проверьте её в `staging`. `DEMO_PASSWORD must be at least 10 characters` — в ветке PR ещё нет кода, который придумывает пароль (он в `main` с 2026-11): влейте в неё свежий `main` и запушьте.
5. В логе выкладки `InvalidSettings: …`, и стенд не стартует. `SECRET_KEY must be at least 32 random characters` — у стенда нет серверного ключа: проверьте, что `SECRET_KEY` задан в `staging` и не запечатан (запечатанные переменные в стенды PR не копируются). `ENV: Input should be …` — у `ENV` неизвестное значение, нужно `staging`.

## Свои пароли стендов PR: что сделать один раз

До 2026-11 стенды PR получали пароль демо-аккаунтов `staging` и общий секрет двухфакторного входа вместе с остальными переменными. Значит, код любой ветки PR мог их прочитать и войти демо-админом на `staging`. Чтобы перейти на свои пароли стендов, после мержа PR с этим изменением в `main`:

1. В `staging`, сервис приложения → **Variables**:
   - задайте `DEMO_PASSWORD` новое значение: старое было в каждом стенде PR;
   - запечатайте `DEMO_PASSWORD` (⋮ → **Seal**);
   - удалите `DEMO_TOTP_SECRET`, если она есть.
2. Там же проверьте, что в `staging` нет секретов production: `VAULT_MASTER_KEY` свой, нет `VAULT_MASTER_KEY_PREVIOUS`, `BACKUP_S3_*`, логина и пароля настоящей почты (`SMTP_USER`, `SMTP_PASSWORD`), нет сервиса `backup`. В базе `staging` не должно быть кабинетов с настоящими клиентами.
3. Сбросьте `staging` (раздел «Сброс стенда»): демо-аккаунты создадутся с новым паролем и без двухфакторного входа. Данные, которые накопили тестировщики, при этом пропадут.
4. Открытые стенды PR сохранили старые значения. Для каждого: влейте в ветку PR свежий `main`, в окружении PR удалите `DEMO_PASSWORD` и `DEMO_TOTP_SECRET` и сбросьте базу стенда. Стенд придумает свой пароль (шаг 8). Новые стенды настроятся сами.
5. **Project Settings → Environments:** **Enable Bot PR Environments** выключен (шаг 8).
6. Передайте новый пароль `staging` тестировщикам лично.

До мержа этого не делайте: ветки без этого изменения не умеют придумывать пароль, и их стенды без `DEMO_PASSWORD` не стартуют (шаг 8, «Если первая выкладка стенда упала», пункт 4).

## Сброс стенда

Если демо-аккаунт поменяли (пароль, почта) или данные надо вернуть в исходное состояние: сервис **Postgres → Settings → Danger → удалить том**, затем **Redeploy** приложения — база создастся пустой и заполнится заново.
