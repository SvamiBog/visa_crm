# Тестовый стенд на Railway: настройка по шагам

Короткая инструкция, когда подписка Railway (тариф Hobby или выше) уже есть. Что такое стенд, демо-аккаунты и проверка на уязвимости — в [staging.md](staging.md); боевой запуск — в [deploy.md](deploy.md).

Что получится:

- окружение `staging` — сайт с вымышленными данными, обновляется после каждого мержа в `main`;
- стенд на каждый PR — своя копия с кодом из ветки PR, обновляется после каждого пуша в PR и удаляется после мержа или закрытия.

## 1. Проект и окружение

1. **Account Settings → Default Region → EU West (Amsterdam)** — данные стенда тоже должны жить в ЕС.
2. **New Project → Empty Project.**
3. Вверху в списке окружений: **+ New Environment → Empty Environment**, имя `staging`. Окружение `production` не трогайте — оно для боевого запуска (deploy.md).

Всё дальше делается в окружении `staging`.

## 2. База

**+ Create → Database → PostgreSQL.** Имя сервиса оставьте `Postgres` — на него ссылаются переменные ниже.

## 3. Приложение

1. **+ Create → GitHub Repo → `SvamiBog/visa_crm`.** Railway попросит доступ к репозиторию — разрешите.
2. В **Settings** сервиса:
   - **Source → Branch:** `main`;
   - **Deploy → Healthcheck Path:** `/api/health`;
   - **Deploy → Restart Policy:** On Failure.
3. **Settings → Networking → Generate Domain.**

## 4. Переменные приложения

Сервис приложения → **Variables → RAW Editor**:

```
ENV=staging
DATABASE_URL=${{Postgres.DATABASE_URL}}
VAULT_MASTER_KEY=<ключ>
SEED_DEMO=1
DEMO_PASSWORD=<пароль демо-аккаунтов, от 10 символов>
DEMO_TOTP_SECRET=<секрет для кодов входа>
SMTP_HOST=${{Mailpit.RAILWAY_PRIVATE_DOMAIN}}
SMTP_PORT=1025
SMTP_TLS=none
MAIL_FROM=VisaCRM staging <no-reply@staging.visacrm.test>
```

Ключ и секрет — в любом Python 3:

```bash
python3 -c "import base64,os;print(base64.b64encode(os.urandom(32)).decode())"   # VAULT_MASTER_KEY
python3 -c "import base64,os;print(base64.b32encode(os.urandom(20)).decode())"   # DEMO_TOTP_SECRET
```

- Ключ стенда — свой, не такой, как в `production`.
- Переменные `staging` не запечатывайте (Seal): запечатанные значения не копируются в стенды PR.
- Пароль и секрет передавайте тестировщикам лично, не в открытых чатах и не в репозитории.

## 5. Ловушка писем Mailpit

Все письма стенда (код смены почты, уведомления) попадают сюда, а не на настоящие адреса.

1. **+ Create → Docker Image →** `axllent/mailpit`, имя сервиса строго `Mailpit`.
2. Переменные:
   ```
   MP_SMTP_BIND_ADDR=[::]:1025
   MP_UI_BIND_ADDR=[::]:8025
   MP_UI_AUTH=tester:<пароль для просмотра писем>
   ```
3. **Settings → Networking → Generate Domain**, порт `8025` — по этому адресу открываются письма. Порт 1025 наружу не открывайте.

## 6. Запуск и проверка

1. **Deploy.** При первом старте применятся миграции и создадутся демо-данные (5 визовиков, по 240–375 клиентов) — около 15 секунд. Повторный старт ничего не дублирует.
2. `https://<домен>/api/health?db=1` должен ответить `"env":"staging"` и `"db":"ok"`.
3. На сайте вверху — оранжевая плашка «Тестовый стенд».

## 7. Вход: где брать код

Демо-аккаунты защищены двухфакторным входом, код — из приложения-аутентификатора:

1. Откройте Google Authenticator, Aegis, 1Password или любой другой аутентификатор.
2. Добавьте аккаунт **«ввести ключ вручную»** (не QR-код): ключ — значение `DEMO_TOTP_SECRET`, тип — по времени (TOTP).
3. Приложение показывает 6-значный код, он меняется каждые 30 секунд. Один и тот же код подходит ко всем демо-аккаунтам.

| Кто | Email | Пароль |
| --- | --- | --- |
| Админ платформы | `admin@demo.visacrm.test` | `DEMO_PASSWORD` |
| Визовики | `visa1@demo.visacrm.test` … `visa5@demo.visacrm.test` | `DEMO_PASSWORD` |
| Сотрудники (без кода) | `visa1.staff@demo.visacrm.test` … `visa5.staff@…` | `DEMO_PASSWORD` |

Если код не подходит — проверьте время на телефоне (должно ставиться автоматически) и что ключ введён без пробелов.

Свой аккаунт, созданный командой `create-admin`, при первом входе после смены пароля сам покажет QR-код для аутентификатора.

Письма (например, код подтверждения при смене почты) читаются в Mailpit по адресу из шага 5.

## 8. Обновления: после мержа и на каждый PR

**После мержа в `main`** окружение `staging` обновляется само: сервис собран из ветки `main`, Railway выкатывает каждый новый коммит.

**На каждый PR — свой стенд:**

1. **Project Settings → Environments → Enable PR Environments**, базовое окружение — `staging`.
2. Когда открывается PR, Railway создаёт окружение `<проект>-pr-<номер>`: копию `staging` со своей пустой базой, Mailpit и приложением из ветки PR. Переменные копируются из `staging`, демо-данные создаются при старте.
3. Каждый пуш в PR пересобирает его стенд; база сохраняется, демо-данные не дублируются.
4. Адрес — в окружении PR: сервис приложения → **Settings → Networking**. Если адреса нет — **Generate Domain**.
5. После мержа или закрытия PR Railway удаляет его окружение сам.

Пока PR открыт, его стенд работает и стоит денег (приложение, база, Mailpit) — старые PR лучше не держать открытыми.

## Сброс стенда

Если демо-аккаунт поменяли (пароль, почта) или данные надо вернуть в исходное состояние: сервис **Postgres → Settings → Danger → удалить том**, затем **Redeploy** приложения — база создастся пустой и заполнится заново.
