# Деплой на Railway

Как выложить VisaCRM на Railway и как дальше выкатываются обновления. Задача бэклога — 0.2.

**Что получится.** Проект на Railway в регионе EU West (Амстердам) из двух сервисов:

- **веб-сервис** — собирается из `Dockerfile` в корне репозитория; в одном контейнере API и собранный интерфейс, поэтому вход по cookie работает на одном домене;
- **PostgreSQL** — база с томом и встроенными резервными копиями Railway.

После настройки каждый мерж в `main` выкатывается сам: GitHub Actions прогоняет тесты, Railway собирает образ, применяет миграции и переключает трафик на новую версию.

Образ проверен локально (2026-10-15): на пустой базе применяются все миграции, `/api/health?db=1` отвечает `db: ok`, админ создаётся командой внутри контейнера, вход ставит cookie с флагом `Secure`.

## Перед началом

- **Аккаунт Railway** на тарифе **Hobby** ($5 в месяц, в них входит $5 ресурсов; ориентировочно этап 1 обойдётся в $10–15 в месяц). Пробный период (Trial) не подходит для реальных данных: том до 0,5 ГБ, а через 30 дней после окончания пробного периода данные удаляются. Карты белорусских банков иностранные сервисы часто не принимают — проверьте оплату заранее.
- **Доступ к репозиторию** `SvamiBog/visa_crm` на GitHub: Railway попросит установить своё GitHub-приложение и выдать ему доступ к репозиторию.
- **Менеджер паролей** (1Password, Bitwarden или аналог) для мастер-ключа сейфа и пароля админа.

## 1. Регион по умолчанию

**Account Settings → регион по умолчанию → EU West Metal (Amsterdam).** Тогда новые сервисы сразу создаются в ЕС.

Регион важно выбрать до появления данных: том базы живёт в регионе своего сервиса, и смена региона потом — это перенос тома с простоем.

## 2. Проект и база

1. **New Project → Deploy PostgreSQL** (или пустой проект, затем **+ Create → Database → PostgreSQL**).
2. Откройте сервис **Postgres → Settings → Region** и убедитесь, что стоит **EU West Metal (Amsterdam)**.

Сервис базы оставьте с именем `Postgres`: на это имя ссылается переменная в шаге 4.

## 3. Веб-сервис из GitHub

1. В проекте: **+ Create → GitHub Repo → `SvamiBog/visa_crm`**. Railway найдёт `Dockerfile` в корне и будет собирать по нему.
2. В **Settings** веб-сервиса:
   - **Region** — EU West Metal (Amsterdam);
   - **Source → Branch** — `main`;
   - **Wait for CI** — включить. Тогда Railway выкатывает коммит, только если тесты в GitHub Actions прошли. Переключатель появляется после того, как Railway получит доступ к результатам GitHub Actions (он покажет баннер с запросом прав).
   - **Deploy → Healthcheck Path** — `/api/health`;
   - **Deploy → Restart Policy** — On Failure.

Последние два пункта записаны и в `railway.json`, но Railway объявил такие файлы («Config as Code») устаревшими: для старых сервисов они работают до 2026-12-01, новые сервисы могут их не читать. Поэтому задаём настройки в панели — так они точно применятся.

## 4. Переменные окружения

Сначала создайте мастер-ключ сейфа — 32 случайных байта в base64. Локально:

```bash
cd backend && uv run python -m app.cli generate-master-key
```

Без локального окружения подойдёт любой Python 3:

```bash
python3 -c "import base64, os; print(base64.b64encode(os.urandom(32)).decode())"
```

**Сначала сохраните ключ в менеджере паролей**, потом вставляйте в Railway. Если ключ потерян, пароли из сейфа и двухфакторный вход не восстановить.

Веб-сервис → **Variables → RAW Editor**, вставить:

```
ENV=production
DATABASE_URL=${{Postgres.DATABASE_URL}}
VAULT_MASTER_KEY=<ключ из менеджера паролей>
```

- `ENV` — любое значение, кроме `local` и `test`: тогда cookie входа ставится только по HTTPS.
- `DATABASE_URL` — ссылка на переменную сервиса базы; Railway сам подставит адрес. Приложение понимает обычный `postgresql://`.
- Письма (код подтверждения при смене почты, уведомления) уходят через SMTP почтового сервиса: `SMTP_HOST`, `SMTP_PORT` (обычно 587), `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_TLS=starttls`, `MAIL_FROM` с адресом на вашем домене. Пока их нет, смена почты в настройках отвечает «Отправка писем пока не настроена». Какой сервис — открытый вопрос (docs/open-questions.md); на тарифах Railway ниже Pro исходящий SMTP может быть закрыт — тогда нужен сервис с HTTP API.
- Файлы клиентов (согласия, договоры, шаблоны документов) — в бакете Railway, переменные `S3_*` ссылаются на него. Как создать бакет — ниже, в «Хранилище файлов». Пока переменных нет, загрузка файла в карточке клиента отвечает «Хранилище файлов пока не настроено».
- `VAULT_MASTER_KEY` после сохранения можно запечатать: меню «⋯» у переменной → **Seal**. Запечатанное значение не видно в панели и не выдаётся через API. Распечатать его нельзя, поэтому запечатывайте только после того, как ключ сохранён в менеджере паролей.

Нажмите **Deploy**, чтобы применить изменения.

### Хранилище файлов

Согласия, договоры и шаблоны документов лежат в бакете Railway в том же проекте (решение — decisions.md → «Хранилище файлов»). Бакет закрыт; файлы шифруются ключом визовика до отправки, в бакете — только шифротекст под ключами из идентификаторов.

1. В окружении **production**: **+ Create → Bucket**.
2. **Region — EU West (Amsterdam)**. Регион потом не поменять. Если EU West в списке нет — не создавайте бакет в другом регионе, сначала решим, что делать.
3. Имя — `Files`: на него ссылаются переменные ниже. Railway даёт новому бакету случайное имя (вроде `adaptable-closet`) — переименуйте его в настройках бакета; имя бакета в S3 (`BUCKET`) от этого не меняется.
4. Веб-сервис → **Variables → RAW Editor**, добавить:

   ```
   S3_ENDPOINT=${{Files.ENDPOINT}}
   S3_REGION=${{Files.REGION}}
   S3_BUCKET=${{Files.BUCKET}}
   S3_ACCESS_KEY=${{Files.ACCESS_KEY_ID}}
   S3_SECRET_KEY=${{Files.SECRET_ACCESS_KEY}}
   ```

   Значения — ссылки: Railway подставит адрес, имя и ключи бакета сам, вставлять их руками не нужно.
5. **Deploy**, затем проверка: в карточке любого клиента загрузите PDF в «Согласие», скачайте его и удалите. Если загрузка отвечает «Хранилище файлов не ответило» — проверьте, что переменные ссылаются на бакет `Files` этого же окружения.

Стоимость — $0,015 за ГБ в месяц, скачивание и запросы бесплатны; объём виден в **Files → Metrics**.

## 5. Домен и проверка

1. Веб-сервис → **Settings → Networking → Generate Domain**. Получится адрес вида `visacrm-production.up.railway.app`.
2. Откройте `https://<домен>/api/health?db=1`. Должно быть:
   ```json
   {"status":"ok","env":"production","db":"ok"}
   ```
3. Откройте `https://<домен>/` — появится страница входа.

Миграции базы применяются сами при каждом запуске (`backend/start.sh`), отдельно запускать их не нужно.

## 6. Первый администратор

Регистрации на сайте нет: первого админа создаёт команда на сервере. Нужен Railway CLI на вашем компьютере:

```bash
bash <(curl -fsSL railway.com/install.sh)   # или: brew install railway / npm i -g @railway/cli
railway login
railway link        # выбрать проект, окружение production и веб-сервис
railway ssh         # оболочка внутри работающего контейнера
```

Внутри контейнера:

```bash
cd /srv/backend
python -m app.cli create-admin you@example.com   # спросит пароль дважды
exit
```

На сервере команды запускаются через `python`, а не `uv run`: `uv run` начнёт докачивать в контейнер инструменты разработки.

Дальше откройте сайт и войдите. Двухфакторный вход — по желанию, но для админа платформы рекомендуется: «Настройки» → «Двухфакторный вход», затем сохраните коды восстановления в менеджере паролей. После этого можно создавать визовиков в админ-панели.

## 7. Резервные копии Railway

**Только на тарифе Pro.** На Hobby Railway не даёт ни расписаний, ни ручных снимков (проверено 2026-10-17: API отвечает «only available for Pro workspaces»), и база остаётся без резервных копий — что делать, решается в docs/open-questions.md.

Сервис **Postgres → Backups**:

1. Включите расписания **Daily** (хранится 6 дней), **Weekly** (1 месяц) и **Monthly** (3 месяца).
2. Нажмите **Enable PITR** — восстановление на любой момент примерно за последние 4 недели. Railway создаст хранилище `Postgres-PITR` и перезапустит базу; хранилище оплачивается по объёму. Окно восстановления начинается с момента включения, поэтому включайте сразу.

Ограничение: если удалить том базы, удалятся и все его копии. Защита от этого — внешний бэкап (задача 0.11): ежедневная зашифрованная копия базы и файлов в Backblaze B2 в ЕС. Настройка и восстановление — [backup.md](backup.md).

## 8. Тестовый стенд

Окружение `staging` с демо-данными и стенды для каждого PR — по шагам в [staging.md](staging.md). У `staging` свой мастер-ключ сейфа и своя база; правка в нём не трогает production.

## Как выкатываются обновления

1. PR мержится в `main`.
2. GitHub Actions прогоняет тесты на `main`; Railway ждёт результата (Wait for CI). Если тесты упали, выкладка пропускается.
3. Railway собирает новый образ, запускает его: `start.sh` применяет миграции и запускает сервер.
4. Railway проверяет `/api/health` и только потом переключает трафик. Если проверка не прошла, продолжает работать старая версия.

**Откат:** веб-сервис → **Deployments** → предыдущая выкладка → меню «⋯» → **Rollback**. Откат возвращает код, но не схему базы: миграции назад не откатываются, поэтому при откате после миграции напишите в задаче, какая версия схемы на сервере.

## Если что-то не так

| Признак | Что проверить |
| --- | --- |
| `"db":"error"` в `/api/health?db=1` | `DATABASE_URL` ссылается на сервис с другим именем; имя в `${{…}}` должно совпадать с именем сервиса базы |
| Выкладка падает на сборке | Логи сборки во вкладке Deployments; чаще всего — сеть до PyPI или npm, помогает повторная выкладка |
| Выкладка падает после сборки, healthcheck не проходит | Логи выкладки: ошибка миграции или пустой `VAULT_MASTER_KEY` |
| Выкладка висит в `WAITING` | Тесты в GitHub Actions ещё идут или упали; через 2 часа Railway пропускает выкладку |
| Не открываются пароли из сейфа или не проходит двухфакторный код после смены ключа | Ротация ключа — по шагам в docs/operations.md |

## Нельзя

- Класть секреты в репозиторий — только в Variables Railway и локальный `.env`.
- Менять регион сервисов после появления данных.
- Удалять том базы: вместе с ним удаляются резервные копии.
- Терять `VAULT_MASTER_KEY`: без него зашифрованные данные не восстановить.
