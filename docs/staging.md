# Тестовый стенд

Стенд — копия системы с вымышленными данными: 5 визовиков, у каждого 240–375 клиентов с консультациями, кейсами на всех этапах, очередями, заявками Франции, сейфом, бронями и поездками; кроме модулей этапа 1 включены калькулятор 90/180, распознавание паспорта и проверка пакета (чек-листы: демо-список для Польши — общий и пара своих пунктов у каждого визовика). На нём можно смотреть изменения до слияния в `main`, давать системе попробовать другим людям и проверять её на уязвимости, не рискуя настоящими данными.

Как это устроено:

- **Окружение `staging` в Railway** — основа: свой Postgres, свой мастер-ключ сейфа, ловушка писем Mailpit.
- **PR-окружения.** На каждый открытый PR Railway сам поднимает копию `staging` с пустой базой и кодом из ветки PR. При старте база заполняется демо-данными, и PR можно открыть в браузере до слияния. Когда PR слит или закрыт, окружение удаляется.
- В `production` демо-данных быть не может: команда `seed-demo` отказывается работать при `ENV=production`.

Короткая настройка по шагам с нуля, когда подписка Railway уже есть, — [staging-setup.md](staging-setup.md). Ниже — подробности.

## 1. Окружение staging

1. Railway → проект → выпадающий список окружений вверху → **+ New Environment → Duplicate Environment** (копия `production`), имя `staging`.
2. В `staging` у веб-сервиса **Variables → RAW Editor**:

   ```
   ENV=staging
   DATABASE_URL=${{Postgres.DATABASE_URL}}
   VAULT_MASTER_KEY=<новый ключ, не как в production>
   SEED_DEMO=1
   DEMO_PASSWORD=<пароль демо-аккаунтов, от 10 символов>
   SMTP_HOST=${{Mailpit.RAILWAY_PRIVATE_DOMAIN}}
   SMTP_PORT=1025
   SMTP_TLS=none
   MAIL_FROM=VisaCRM staging <no-reply@staging.visacrm.test>
   ```

   - Ключ: `uv run python -m app.cli generate-master-key`. Не запечатывайте (Seal) переменные `staging`: запечатанные значения не попадают в PR-окружения.
   - `DEMO_TOTP_SECRET` — по желанию: с ней у демо-админа и демо-визовиков включён двухфакторный вход. Любая строка base32 из 16–32 символов, например из `python3 -c "import pyotp; print(pyotp.random_base32())"`. Этот секрет добавляют в приложение-аутентификатор (Google Authenticator, Aegis, 1Password — «ввести ключ вручную»), и оно показывает коды для входа во все демо-аккаунты.
   - Пароль и секрет передавайте тестировщикам лично, не в открытых чатах и не в репозитории.

3. **Mailpit** — ловушка писем: всё, что отправляет стенд (коды смены почты, уведомления), попадает в неё, а не на настоящие адреса. **+ Create → Docker Image** → `axllent/mailpit`, имя сервиса `Mailpit`. Его переменные:

   ```
   MP_SMTP_BIND_ADDR=[::]:1025
   MP_UI_BIND_ADDR=[::]:8025
   MP_UI_AUTH=tester:<пароль для просмотра писем>
   ```

   **Settings → Networking → Generate Domain**, порт `8025`: по этому адресу открываются письма (логин и пароль из `MP_UI_AUTH`). Порт 1025 наружу не открывать — приложение ходит к нему по внутренней сети Railway.

4. Сгенерируйте домен для веб-сервиса (**Settings → Networking → Generate Domain**) и задеплойте. При старте `start.sh` применит миграции и, раз `SEED_DEMO=1`, заполнит пустую базу (около 15 секунд). Повторный запуск ничего не дублирует.
5. Откройте адрес: сверху страницы должна быть оранжевая плашка «Тестовый стенд».

Веб-сервис `staging` пусть собирается из `main` — это стенд «как сейчас в main» с накопленными данными тестировщиков.

## 2. Стенд для каждого PR

1. Railway → проект → **Settings → Environments → Enable PR Environments**, базовое окружение — `staging`.
2. Теперь на каждый PR Railway создаёт окружение `<проект>-pr-<номер>` со своей пустой базой, Mailpit и веб-сервисом из ветки PR; переменные копируются из `staging`. Адрес — в окружении PR (вкладка сервиса → Settings → Networking). Если Railway не создал адрес сам — **Generate Domain**.
3. Каждый пуш в PR переразвёртывает стенд; база при этом остаётся, демо-данные не дублируются.

Пока PR открыт, его стенд работает и стоит денег (веб-сервис, база, Mailpit). Слитые и закрытые PR Railway удаляет сам.

## 3. Вход для тестировщиков

Все демо-аккаунты — с паролем из `DEMO_PASSWORD`. Двухфакторный вход — по желанию (включается в «Настройках»); если задана `DEMO_TOTP_SECRET`, у админа и визовиков он уже включён и код берётся из приложения-аутентификатора с этим секретом:

| Кто | Email | Что проверять |
| --- | --- | --- |
| Админ платформы | `admin@demo.visacrm.test` | Визовики, справочник стран, общий журнал |
| Визовики 1–5 | `visa1@demo.visacrm.test` … `visa5@demo.visacrm.test` | Вся работа с клиентами; каждый видит только своих |
| Сотрудники | `visa1.staff@demo.visacrm.test` … `visa5.staff@…` | Только «Клиенты» и «Кейсы», без сейфа |

Почта демо-аккаунтов и клиентов — несуществующие адреса; письма читаются в Mailpit. Если кто-то сменил пароль или почту демо-аккаунта, верните стенд в исходное состояние сбросом.

**Сброс.** Удалить том базы окружения (сервис Postgres → Settings → Danger) и задеплоить веб-сервис заново: база создастся пустой и заполнится демо-данными. У PR-стенда база и так одноразовая: следующий PR начнёт с чистой.

## 4. Проверка на уязвимости

**Только стенд, никогда production.** Цели — адрес стенда и его Mailpit; инфраструктуру Railway, GitHub и чужие сервисы не трогаем. Нагрузочные атаки (DoS) не устраиваем: стенд на общем тарифе.

Что уже проверяется само, на каждом PR (GitHub Actions, задание `security`):

- зависимости Python (`pip-audit`) и npm (`npm audit`, high и critical) на известные уязвимости — **блокирует слияние**;
- ZAP baseline — пассивная проверка запущенного приложения с демо-данными: заголовки, cookie, утечки в ответах. Отчёт — в артефакте `zap-report` запуска; сам он слияние не блокирует, его читают.

Что проверять руками (OWASP Top 10 применительно к нам):

- **Чужие данные.** Под `visa1` взять id клиента, кейса, брони, учётки из сейфа и попробовать открыть или изменить их под `visa2` — должно быть «не найдено». Сотрудник без модуля не должен видеть сейф ни через интерфейс, ни через API.
- **Вход.** Перебор паролей (после 10 ошибок — блокировка на 15 минут), повтор кода 2FA, обход шага 2FA, вход после смены пароля на другом устройстве.
- **Сейф.** Пароль не приходит ни в одном ответе, кроме «Показать»; каждый показ — в журнале.
- **XSS.** Скрипты и HTML в именах, заметках, названиях отелей, логинах — должны показываться текстом.
- **Смена почты.** Без пароля, чужим кодом, перебором кода (после 5 ошибок код сгорает), на занятый адрес.
- **Заголовки.** CSP, `X-Frame-Options`, HSTS, `X-Robots-Tag: noindex` (стенд не должен попадать в поиск).

Найденное — в issue репозитория; уязвимость, которую можно повторить на production, — не в открытый issue, а лично владельцу.

**Известное:** `npm audit` показывает две уязвимости средней тяжести в `react-router` 6 (открытый редирект через обратный слэш в `<Link>` и `useNavigate`; вторая — про серверный рендеринг, его у нас нет). Исправление — переход на `react-router` 7, отдельная задача.
