# Журнал решений

Принятые решения по продукту. Новое решение — новая строка сверху раздела; отменённое не удаляем, а помечаем «отменено» со ссылкой на новое.

## Модель работы и доступы

- Сотрудники (2026-10-15): визовик сам приглашает сотрудника (имя, email, разделы), система выдаёт временный пароль, как при создании визовика. Визовик может менять разделы, блокировать и выдавать новый пароль (он же сбрасывает 2FA и закрывает сессии сотрудника). Журнал и раздел «Сотрудники» видит только визовик. Доступ сотрудника к отдельным кейсам появится вместе с кейсами (задача 1.4).
- Сотрудники: только свои кейсы (2026-10-25, решение владельца, вопрос 17): сотрудник видит только кейсы, которые визовик отметил в самом кейсе (блок «Доступ сотрудников»), остальные кейсы их групп подачи, карточки клиентов всех этих кейсов, а также клиентов и кейсы, которые завёл сам. Остальной картотеки для него нет — ни в списке и поиске, ни на главной, в очередях, бронях, напоминаниях и аналитике. Ограничение держит база (политика `employee_scope`, миграция 0031), а не только код. Номер нового кейса и проверка дубля по телефону считаются по всему кабинету; если номер уже есть у чужого для сотрудника клиента, он узнаёт только, что номер занят. «Регистраторы» и долги регистраторам — только визовику: баланс считается по всем кейсам. Импорт — по-прежнему только визовик.
- Группы подачи меняет только визовик (2026-11-21, решение владельца по аудиту безопасности, находки M1 и L1, задача S2): выданный сотруднику кейс открывает ему всю свою группу подачи, поэтому объединять кейсы в группу и выводить их из неё может только визовик, так же как выдавать доступ к кейсу. Сотрудник видит, с кем подан кейс, но кнопок группы у него нет, а API отвечает ему 403 `forbidden`. Группа распускается по её реальному составу, и каждый снятый кейс пишется в журнал как `cases.ungrouped`.
- Пароли к смене при уходе сотрудника — по журналу (2026-11-22, аудит безопасности, находка M2, задача S3): в списке «Открытые пароли» — пароли, которые сотрудник показал, а также записи, которые он добавил или которым сохранил пароль: их он знает без показа. Пароль считается сменённым, только если после этого его сохранил кто-то другой; время сохранения и удаление записи этого не доказывают, потому что сотрудник может сохранить тот же пароль ещё раз или удалить запись. Удалённая запись остаётся в «Осталось сменить»: учётная запись на сайте продолжает жить; клиент и сайт берутся из журнала, логина в журнале нет. Пароль, убранный из сейфа, тоже остаётся к смене. Сотрудник удаляет из сейфа только записи, которые добавил сам (403 `forbidden`), как файлы.
- Поиск и карточка без модуля «Кейсы» (2026-11-22, решение владельца, аудит безопасности, находка L3, задача S8): пользователь без модуля «Кейсы» не получает из картотеки ничего о кейсах, даже если кейсы ему выданы. Вкладки и счётчики считаются так, будто у клиента нет кейсов, по последней консультации: «Думают» при решении «думает», «Архив» при «нет», иначе «Консультации»; «В работе» у такого пользователя пустая. Номер заявки ВЦ в строке поиска не ищется. Фильтры этапа и регистратора, если пришли в запросе, молча не учитываются, без ошибки, чтобы старая ссылка открывала список. Фильтр по стране смотрит только на страны последней консультации. В карточке не показываются и кейсы, открытые из консультаций (номер, направление, этап, результат). С модулем всё работает как раньше.
- Защита данных от копирования сотрудником (2026-10-25, решение владельца): полностью запретить копирование нельзя (экран можно сфотографировать), поэтому сотрудник видит меньше, массовые просмотры видны и ограничены, увольнение закрывает доступ. Выбраны: только свои кейсы (Т.13), журнал просмотров, дневные лимиты и сигнал визовику (Т.14), отключение со списком открытых паролей (Т.15). Пока не делаем: скрытые телефоны и паспорт с показом по кнопке, обязательная 2FA и короткая сессия для сотрудников, водяной знак на экране. Запрет выделения текста и правой кнопки не делаем вовсе: обходится за минуту.
- Модули (2026-10-15): 23 модуля из карты PRD — список в коде (`app/core/modules.py`), потому что модуль — это функция программы. Новому визовику по умолчанию включены модули этапа 1 (клиенты, кейсы, сейф учётных записей, финансы кейсов, задачи, справочник стран, аналитика; сейф и финансы добавлены 2026-10-16); админ меняет набор в «Настроить». Сотрудник получает только модули, которые есть у визовика и которые визовик ему выдал; модуль, отключённый у визовика, пропадает и у сотрудников. Доступ к модулю проверяется в API (`require_module`).
- Налог визовика (2026-10-15): ставка в процентах задаётся админом при создании и в настройках (по умолчанию в форме 10% — НПД).
- Журнал действий (2026-10-15): таблица только для добавления — изменить или удалить запись не может ни приложение, ни владелец базы (триггер). Визовик видит только то, что сделали он сам и его сотрудники; действия админа над его кабинетом и команды платформы в его журнал не попадают (изменено 2026-10-16). Админ видит все события и фильтрует их по кабинету (или только платформа — вне кабинетов), пользователю, разделу, событию и датам, от новых к старым или наоборот; у визовика те же фильтры в пределах его кабинета. Фильтры передаются в адресе запроса — это идентификаторы, даты и названия событий, без данных клиентов. Сотрудники журнал не видят. Пишутся входы и неудачные попытки (по известным email, чужие email не сохраняются), блокировки, выходы, смена пароля, включение и сброс 2FA, действия админа над визовиками, команды CLI; IP-адрес — для расследования инцидентов. Персональных данных клиентов в журнале нет: только идентификаторы.
- Удаление всех данных кабинета (2026-11-16, решение владельца, задача 1.23): визовик, который переходит в другую систему, сам удаляет в «Настройках» всё, что вёл в CRM: клиентов, кейсы, консультации, платежи, сейф, файлы в хранилище, брони, очереди, направления, шаблоны, импорты и сотрудников; справочники возвращаются к стандартным, как у нового кабинета. Остаются вход визовика, настройки кабинета, подписка с оплатами и журнал действий (в нём только идентификаторы; защита журнала не ослабляется, сама очистка тоже пишется в него). Только визовик, не сотрудник и не админ; только с включённой двухфакторной защитой; подтверждение — пароль и код из приложения-аутентификатора (код восстановления не подходит), ошибки считаются с неудачными входами. Ключ сейфа удаляется вместе с паролями, новый создаётся при следующем пароле. В резервных копиях данные остаются до 12 месяцев (backup.md) и стираются по сроку. Код — `app/core/erase.py`: удаляются все таблицы с `tenant_id`, кроме перечисленных в `KEPT_TABLES`, так что новая таблица попадает под очистку сама.
- Двухфакторный вход (2026-10-15; 2026-10-17 — по желанию для всех; 2026-11-03 — включение с паролем): ~~обязателен для админа и визовика~~ — с 2026-10-17 по желанию для всех ролей (решение Максима): включается в «Настройках» или по ссылке в меню — с 2026-11-03 сначала паролем аккаунта, и только потом показывается QR-код (аудит 6.2: иначе тот, кто сел за открытый чужой кабинет, подключил бы своё приложение и забрал коды восстановления), — выключается там же паролем и кодом из приложения (или кодом восстановления), выключение пишется в журнал. Если включён — при входе нужен код. Приложение-аутентификатор (TOTP, код из 6 цифр, допускается расхождение часов на 30 секунд), 10 одноразовых кодов восстановления. Один и тот же код не принимается дважды. Неверные коды считаются вместе с неверными паролями (10 подряд — блокировка на 15 минут). ~~Подключение — сразу после смены временного пароля, до этого кабинет не открывается.~~ Кабинет открывается сразу после смены временного пароля. «Новый пароль» в админке сбрасывает и двухфакторный вход; админу, потерявшему телефон и коды, — команда `reset-two-factor` на сервере.
- Утечка мастер-ключа и коды восстановления (2026-11-23, решение владельца, аудит безопасности, находки L6, h02.3, h02.7, h02.8, задача S16): плановая ротация мастер-ключа по-прежнему меняет только обёртку ключей кабинетов. На случай утечки есть отдельная команда `rekey-after-leak` (docs/operations.md): каждому кабинету новый ключ данных, пароли сейфа и файлы в хранилище (документы, шаблоны) перешифровываются на месте, у всех пользователей выключается двухфакторный вход и удаляются коды восстановления, все сессии завершаются. Команда работает только с новым `VAULT_MASTER_KEY` и утёкшим ключом в `VAULT_MASTER_KEY_PREVIOUS`; каждый кабинет меняется в своей транзакции, а повторный запуск после сбоя приходит к тому же ключу без хранения состояния. Коды восстановления хранятся как HMAC с ключом, выведенным из `SECRET_KEY`; старые коды принимаются и переводятся при использовании, остальные переводит команда `upgrade-recovery-codes`. Смена `SECRET_KEY` делает недействительными все выданные коды восстановления (вход по коду из приложения работает), поэтому `SECRET_KEY` меняют только при утечке, вместе с `rekey-after-leak`, которая и так удаляет все коды. Если ключ сменили иначе, возвращают прежнее значение; если его нет, каждый с двухфакторным входом выключает и снова включает его в «Настройках» и получает новые коды, а потерявшему ещё и телефон двухфакторный вход сбрасывают как обычно (визовику — админ, сотруднику — визовик, админу — `reset-two-factor`). Код TOTP принимается только из цифр ASCII.
- Вход (2026-10-15): сессия живёт 7 дней с момента входа; после 10 неверных паролей подряд вход блокируется на 15 минут; пароль — не короче 10 символов; при смене пароля остальные устройства выходят. Админ может выдать визовику новый временный пароль — это же снимает блокировку. Блокировка визовика в админке закрывает вход и ему, и его сотрудникам.
  - Пароль в «Настройках» (2026-11-03, аудит 6.2): смена пароля, смена почты, включение и выключение двухфакторного входа спрашивают текущий пароль, и неверный пароль (и неверный код при выключении 2FA) считается вместе с неверными паролями при входе — через украденную сессию пароль не подобрать. Пока аккаунт заблокирован, эти формы пароль не проверяют, а отвечают «слишком много попыток» и закрывают все сессии аккаунта; так же — на неверной попытке, которая блокирует аккаунт. Вход дальше — через страницу входа, когда пройдут 15 минут.
  - Одновременные попытки (2026-11-03, аудит 6.2): попытки входа в один аккаунт идут по очереди, поэтому пачка одновременных неверных паролей проверяет не больше 10, остальные получают ~~«слишком много попыток»~~ с 2026-11-22 тот же ответ, что неверный пароль (задача S9). Для неизвестной почты пароль сверяется с подставным хешем, чтобы по времени ответа нельзя было узнать, есть ли такой аккаунт.
  - Блокировка входа не выдаёт аккаунт (2026-11-22, аудит безопасности, находки L4, N6, h01.2, h01.7, h02.1, задача S9): пока аккаунт заблокирован после 10 промахов, страница входа отвечает так же, как для адреса без аккаунта, «Неверный email или пароль», и даже верный пароль сверяется с подставным хешем, поэтому ни ответ, ни время не говорят, есть ли аккаунт. Срок блокировки прежний, 15 минут. «Слишком много попыток» остаётся в формах настроек и на втором шаге входа, где пароль уже известен. С одного адреса клиента — не больше 30 неудачных входов за 15 минут по любым адресам почты; дальше «Слишком много неудачных попыток. Попробуйте через 15 минут.» ещё до проверки пароля, даже верного. Удачный вход в этот счёт не идёт. Счёт хранится в памяти сервиса, перезапуск его обнуляет; надёжным по адресу он станет, когда адрес клиента будет браться только от прокси Railway (S17). Пароль проверяется вне транзакции и не держит соединение с базой; одновременно проверяются не больше двух паролей, остальные ждут очереди. Включение и выключение двухфакторного входа закрывает все остальные сессии аккаунта, в том числе входы, ждущие кода; неверные коды при включении считаются вместе с неверными паролями, как при выключении.
  - Cookie сессии (2026-11-23, аудит безопасности, находка N10, задача S18): там, где сайт работает по HTTPS (все окружения, кроме машины разработчика с `ENV` `local` или `test`), cookie входа называется `__Host-visacrm_session`: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`. Такую cookie браузер принимает только от самого сайта, поэтому соседний сайт под тем же родительским доменом (другой адрес на `up.railway.app`, другой поддомен своего домена) не может подложить свою сессию. На машине разработчика по http имя прежнее, `visacrm_session`: префикс требует `Secure`. Если cookie сессии пришла дважды под одним именем, сервер не верит ни одной копии и отвечает 401; если пришли оба имени, верит только `__Host-`. Переход без массового выхода: до 21.12.2026 сервер по HTTPS принимает и старое имя, в ответ выставляет новую cookie на остаток сессии и стирает старую; после этой даты старое имя не принимается. Выход стирает cookie под обоими именами.
- Первого админа платформы создают командой `python -m app.cli create-admin` на сервере; других способов создать админа нет (2026-10-15).

- Сотрудники визовика закладываются с этапа 0: визовик выбирает их модули и кейсы и видит их действия в журнале.
- Доступ к модулям гибкий: админ включает модули каждому визовику вручную.
- Аккаунт визовика создаёт админ и выдаёт временный пароль; при первом входе визовик обязан сменить пароль на свой (2026-10-15).
- Регистрации «с улицы» нет (2026-10-15).
- Верификация клиента (KYC) отложена.

- Смена почты (2026-10-16): каждый пользователь меняет почту для входа в «Настройках». Нужны текущий пароль (неверный считается вместе с неверными паролями входа) и 6-значный код, который приходит на новый адрес: он действует 30 минут, 5 неверных вводов — код сгорает, новый можно запросить через минуту, отмена паузу не снимает. Код хранится только хешем. После смены на прежний адрес уходит уведомление с замаскированным новым адресом, остальные устройства выходят, как после смены пароля. В журнал — «запрошена смена почты» и «почта изменена», без адресов.
  - Попытки кода и письма в день (2026-11-22, аудит безопасности, находки L5, h17.3, задача S10): каждый ввод кода занимает одну из пяти попыток до проверки, поэтому коды, отправленные одновременно, не обходят лимит. Пятый промах помечает код истёкшим, а не удаляет его, и новый код по-прежнему можно запросить только через минуту. Одному пользователю уходит не больше 10 писем с кодом за 24 часа (считаются по журналу действий); 11-й запрос получает «Код только что отправлен…» — отдельный текст для дневного лимита появится вместе со своим кодом ошибки.

- Проверка источника изменяющих запросов (2026-11-23, аудит безопасности, заметка h01.3, задача S19): POST, PUT, PATCH и DELETE принимаются только со страниц самого сайта, иначе 403 `forbidden`. Решает `Sec-Fetch-Site` (`same-origin` или `none`); без него — `Origin`, который должен совпасть с `Host` или `X-Forwarded-Host`. Запрос без обоих заголовков проходит: его прислал не браузер, а подделать запрос от имени визовика может только браузер, который сам добавляет cookie и при этом всегда шлёт `Origin`. Настраивать ничего не нужно: свой адрес берётся из запроса. Тест — `tests/test_request_origin.py`.
- Ошибки у полей (2026-11-18, по итогам UI/UX-аудита 2026-11-17): ошибка, которая относится к одному полю, показывается прямо под ним красным текстом, у поля красная рамка, `aria-invalid` и `aria-describedby` на сообщение (сначала ошибка, потом подсказка поля). После неудачной отправки фокус переходит на первое такое поле, и экранный диктор читает название поля и ошибку. К полю ошибку относят коды API, которые форма сопоставила с полем (`phone_taken` к телефону, `same_country` к стране подачи, `invalid_credentials` к паролю), и проверка самого API (ответ 422), которая называет поле. Ошибка без поля (нет связи, лимит, «не найдено») остаётся общим сообщением над кнопками формы, а не вверху: в длинной форме на телефоне верх уходит за экран. Так устроены все формы, где ошибка может относиться к одному полю. У поля без своей подписи (ячейка строки списка: условия партнёра, цены регистратора, предоплаты, оплата консультации; название, которое правят на месте) сообщение стоит под строкой. Где сохранение идёт без кнопки отправки (дата документа в пакете, выбор файла импорта, период аналитики, проверка строк паспорта), сообщение тоже под полем, но фокус остаётся на месте. Как это сделать в форме — `Field`, `useFieldErrors`, а для ячейки строки `invalidProps` и `RowError` в `frontend/src/components/Field.tsx`.
- Свои шрифты (2026-11-18, по итогам UI/UX-аудита 17.11.2026): шрифты тем (Onest, Inter, Manrope, Lora, IBM Plex Sans, IBM Plex Mono) отдаёт наш сервер, а не Google Fonts. Раньше каждая страница сначала запрашивала таблицу стилей у fonts.googleapis.com, а файлы — у fonts.gstatic.com: отрисовка ждала чужой сайт, и IP-адрес визовика уходил Google, что спорно по GDPR для CRM с данными клиентов. Файлы берём из npm-пакетов Fontsource (лицензия SIL OFL 1.1 лежит в каждом пакете), правила `@font-face` — в `frontend/src/fonts.css`. CSP теперь пускает стили и шрифты только со своего домена. Набор тот же, что был у Google: начертания 400–700 (у Lora 500–700, у Plex Mono только 500), латиница и кириллица, расширенная латиница для польских, чешских и литовских имён и, у Onest и Lora, символы (стрелки «←», «→»). Браузер скачивает файл, только когда на странице есть его знаки и тема использует это семейство. Первый заход со сброшенным кэшем, шрифты: синяя тема 48,5 КБ (у Google было 42–52 вместе с его таблицей стилей), тёмная 65,4 (69,3), тёплая 96,1 (100–103), минимал 73,5 (77,3) и ещё 14,5 КБ Plex Mono на главной. Google отдаёт файлы по-разному от раза к разу, отсюда разброс. Правила `@font-face` добавили к CSS сайта 8,7 КБ (1,2 КБ в gzip), так что по байтам первый заход почти тот же, зато без двух чужих доменов и без ожидания чужой таблицы стилей. Файлы шрифтов, как и остальная сборка, кэшируются на год. В сборке 20 файлов шрифтов на 529 КБ, но скачиваются только нужные. Вид не изменился: на всех проверенных экранах всех тем текст рисуется теми же шрифтами тех же версий, скриншоты совпадают попиксельно, кроме сглаживания отдельных знаков.
- Подтверждение и отмена удаления (2026-11-17, по итогам UI/UX-аудита): системное окно браузера (`window.confirm`) больше не используем. Оно не в теме сайта, не переводится на язык CRM и на телефоне выглядит чужим. Вместо него два способа.
  - **Окно подтверждения в стиле сайта** — для тяжёлых и необратимых действий: удалить карточку клиента, файл, учётную запись сейфа, шаблон, бронь, партнёра, регистратора, направление, оплату подписки; выключить город, партнёра, регистратора, направление; заблокировать визовика или сотрудника и выдать ему новый пароль; отменить заявку; убрать кейс из группы подачи. Красная кнопка называет действие («Удалить», «Выключить», «Заблокировать»). Фокус сначала на кнопке отказа, чтобы случайный Enter ничего не удалил; Escape и нажатие мимо окна — тоже отказ. Перенос кейса по доске и открытие кейса из лида спрашиваются тем же окном, но с обычной синей кнопкой: это не опасно, окно только ловит случайное перетаскивание.
  - **«Удалено · Отменить» без окна** — для мелкой записи, которую визовик завёл сам и удаление которой ничего не тянет за собой: заметка, поездка, платёж или расход кейса, оплата регистратору, шаблон в карточке клиента. Сюда же очистка калькулятора 90/180: там всё в браузере, сервер не участвует. Запись остаётся на месте зачёркнутой, внизу экрана 7 секунд висит «Отменить» (время стоит, пока на сообщении курсор или фокус). Запрос на удаление уходит, только когда время вышло, поэтому суммы финансов до этого не меняются. Сервер ничего не восстанавливает: мягкого удаления нет и не вводим, иначе каждый список, сумма и отчёт должны помнить о скрытых записях, и один забытый фильтр испортит деньги. Журнал пишет удаление, когда оно случилось; отменённое удаление в журнал не попадает, потому что его не было.
  - **Закрытие вкладки.** Отложенное удаление уходит сразу, если вкладку закрывают, перезагружают, уходят с сайта или прячут (на телефоне свернули браузер), и перед выходом из CRM. Запрос уходит с `keepalive`, и браузер доводит его после закрытия страницы. Если браузер упал или телефон выключился в эти секунды, запись останется: потеряться может только удаление, не данные. Если сервер отказал (нет прав, запись уже удалили, нет сети), появится ошибка, и запись вернётся в список. Ждёт одно удаление за раз: следующее отправляет предыдущее сразу.

- Размер запроса (2026-11-10; пересмотрено 2026-11-21 по аудиту безопасности, находка M7, задача S1): тело формы не больше 256 КиБ, более крупный запрос сервер отклоняет, не читая (413, «Запрос слишком большой»). FastAPI разбирает JSON целиком до любой проверки, даже до проверки входа. В памяти разобранное тело занимает в десятки раз больше самого запроса, и пока идёт разбор, единственный веб-процесс никому не отвечает. Самая большая форма — анкета: меньше 230 КБ, даже если каждый символ занимает 4 байта. Подтверждение импорта шлёт только значения, выбранные вручную. До 16 МБ принимаются только четыре маршрута с файлом: документ клиента, файл импорта, новый шаблон и замена файла шаблона. И только с действующей сессией: предел проверяет её сам, так же как API, поэтому выдуманной cookie или входа без второго шага мало. Файлы идут внутри JSON в base64 (на треть больше файла); самый большой файл, который принимает CRM, — 10 МБ, он проходит. Пределы самих файлов и их сообщения прежние. Ответ 422 называет поле и причину, но не возвращает присланное, и ошибок в нём не больше 100. Код — `app/core/request_limit.py`, обработчик 422 — `app/main.py`.

Сессии входа и коды восстановления создаёт и меняет только системная область; визовик видит и удаляет такие строки аккаунтов своего кабинета (так он завершает сессии сотрудника), сотрудник — только свои. На всех соединениях приложения заданы `lock_timeout` 10 с и `idle_in_transaction_session_timeout` 5 мин: запрос, который ждал бы чужую долгую транзакцию (например, создание кейса во время импорта того же кабинета), получает ошибку через 10 с и не держит соединение пула, а забытая открытой транзакция закрывается через 5 минут. ## Слоты и SaaS

- Оплата визовиков (2026-10-28, решение владельца): две отдельные оплаты — подписка на CRM и оплата за каждый слот в визовом центре, который получила система (модуль слотов). С этапа 3 есть только подписка: админ ведёт её в админ-панели и сам отмечает поступившие оплаты, онлайн-оплаты в системе нет. Оплата за слоты появится вместе с модулем слотов (этап 7): каждый успешный слот (ниже) — начисление, которое оплачивается отдельно от подписки. Цена подписки (одна для всех или своя у каждого визовика), периодичность и пробный период — open-questions.md, до этапа 3; цена за слот, отмены и переносы — до этапа 7. _Подписка решена 2026-10-30 — ниже._
- Подписка визовиков (2026-10-30, решение владельца, задача 3.8):
  - Тарифы общие для всех. У тарифа есть название, цена в месяц и валюта; админ назначает тариф визовику. Новая цена тарифа действует у всех визовиков на нём со следующей оплаты, а прошлые оплаты сохраняют записанные суммы. Тариф, который больше не действует, нельзя назначить, но у визовиков, которые на нём уже есть, он остаётся. Перерасчёта части месяца при смене тарифа нет.
  - Оплата раз в месяц. Даты оплат идут по календарю от первой оплаты: 31-е число в коротком месяце становится последним днём месяца. Поздняя оплата календарь не сдвигает.
  - Пробный период задаётся датой у визовика и может быть пустым. Первая оплата приходится на конец пробного периода, а без него — на дату начала подписки (день, когда назначен тариф; админ может её изменить).
  - Админ отмечает оплату: дату, сколько месяцев она покрывает, сумму, валюту и заметку. Без суммы записывается цена тарифа × месяцы. Ошибочную оплату админ удаляет. Каждое изменение подписки пишется в журнал с привязкой к кабинету визовика: админ видит его в журнале по этому визовику.
  - Статусы: «пробный», «оплачено», «скоро оплата» (за 7 дней до даты), «просрочено» (на следующий день после даты), «нет подписки» (тариф не назначен). «Сегодня» считается в часовом поясе визовика.
  - На главной админки — просроченные и ближайшие оплаты, без заблокированных визовиков.
  - Визовик видит свою подписку в «Настройках» только для просмотра. При просрочке вверху кабинета показывается плашка. Сотрудники визовика подписку не видят.

## Клиенты и кейсы

- Партнёра и регистратора можно удалить (2026-11-15, решение владельца). Раньше записи справочников только выключались. Теперь у партнёров и регистраторов есть «Удалить» в строке списка и в форме правки, как у направлений. Партнёр удаляется, если его не указали ни в одной карточке клиента: по карточке кейсы клиента берут условия партнёра, а аналитика считает приход от партнёров. Регистратор удаляется, если его нет ни в одном кейсе и ему не было платежей. Условия партнёра и прайс регистратора удаляются вместе с ним. Используемую запись сайт предлагает выключить: она пропадёт из списков, а карточки, кейсы и расчёты останутся как были. Удаление пишется в журнал кабинета.
- Даты — только с годом от 1900 до 2100 (2026-11-10, техническое решение по итогам проверки проекта): любая дата, которую вводят в карточке, консультации, кейсе, очереди, брони, финансах и подписке, и любая дата из файла импорта принимается только в этих пределах. Год с опечаткой проходил и через форму (браузер оставляет «0026», если набрать «26»), и через таблицу («05.11.0026» — тоже дата) и сохранялся: подача с таким годом не попадала ни в «Требует внимания», ни в «Ближайшие подачи», а карточка клиента с отказом, решённым до 1990 года, переставала открываться. Теперь форма отвечает «Проверьте заполнение полей», импорт — «значение вне допустимого» по ячейке; строка с такой датой в обязательной колонке пропускается, в необязательной — пропускается только ячейка. Даты паспорта и прошлых виз в анкете консультации не ограничены: анкета хранится в карточке как есть, её проверки принимают любую дату. Границы — `app/core/days.py`; то, что каждое поле-дата API их держит, проверяет `tests/test_days.py`.
- Кейс = одна виза одного заявителя. Семья, подающаяся вместе, — группа подачи из нескольких кейсов; у каждого своя карточка и стоимость.
- У членов семьи могут быть разные страны и цели.
- Порядок этапов: консультация → ожидание записи → сбор документов (после того как пришла дата) → подача → рассмотрение → результат; ветка апелляции.
- Результат визы — структурированные поля (итог, тип, срок действия, дней пребывания, после апелляции); многократные визы в аналитике делятся по сроку: до 3 мес., 3–12 мес., 1–5 лет.
- Апелляции — только там, где их принимают в Беларуси (поле справочника стран).
- Сканы паспортов и документов остаются в Telegram; система по умолчанию сканы не хранит. Согласие на обработку данных и договор фиксируются с каждым клиентом (дата + файл).
- Данные карточек хранятся бессрочно; по просьбе клиента карточка удаляется или обезличивается.
- Оплата консультации засчитывается в стоимость всегда, даже через полгода.
- Регистраторы — компании или частные лица; ставят клиентов в лист ожидания через свою CRM. Оплата за талон, пачкой или из аванса; цена зависит от страны, цели и зала. _Уточнено 2026-10-27 (вопрос 11): регистраторы и ловят прямые слоты при раздаче — Испанию вручную, Болгарию, Венгрию и Хорватию ботом. Регистратор и зал в кейсе нужны поэтому не только странам с листом ожидания._
- Тип идентификатора в визовом центре задаётся страной (ID, номер заявки, номер анкеты, имя пользователя).
- Почта заявки может быть клиента, созданная визовиком или регистратора.
- Подача возможна в Беларуси (все города) и в Турции, Сербии, Грузии, Армении. _2026-10-27: по словам визовика, в Турции, Сербии, Армении и Грузии запись устроена совсем иначе, чем в Беларуси — правила для них заводим после вопроса 29._
- Объём работы (2026-10-27, ответ визовика на вопрос 9): в работе 88 клиентов, многие стоят в очереди на Италию, Польшу и Германию; новых — от 5–7 до 15–20 в месяц. Это отправная точка для метрики «активных кейсов на одного визовика» (PRD) и для лимитов активных кейсов, когда платформа откроется другим визовикам (эпик 3.1). Демо-стенд с ~300 клиентами на визовика проверяет объём с запасом.

- Контакт (2026-10-15): один телефон — одна карточка у визовика (номер хранится в формате E.164 с кодом страны, «+375 (29) …» и «375…» считаются одним номером); при дубле система показывает уже существующую карточку. Поиск — по ФИО (кириллица и латиница), части телефона и Telegram; текст поиска передаётся в теле запроса, а не в адресе, чтобы персональные данные не попадали в URL и логи. В журнале по контактам — только идентификаторы и названия изменённых полей, без значений. Заметку меняет её автор или визовик. Связи между контактами двусторонние, у каждой стороны своя подпись («муж» / «жена»). Сотрудник с модулем «Клиенты» видит всех клиентов визовика; ограничение по кейсам — вместе с кейсами (1.4).
- ФИО по частям и паспорт в карточке (2026-10-24, запрос владельца): в форме клиента фамилия, имя и отчество — отдельные поля; обязательно что-то одно из фамилии и имени (клиента с консультации часто знают только по имени). Латиницей, как в паспорте, — фамилия и имя (имена) отдельно, распознавание паспорта переносит их из машиночитаемой зоны по отдельности. Карточка хранит части, а полное имя («Фамилия Имя Отчество») собирается из них и хранится рядом — его показывают списки, по нему ищут и склеивает людей импорт; что оно совпадает с частями, проверяет база. Так же, тремя полями, вводится новый член семьи при открытии кейса. Имя одной строкой (ячейка таблицы при импорте) делится по правилу: одно слово — имя, иначе фамилия, имя, остальное — отчество (латиницей: фамилия, остальное — имена); так же при переходе разделены имена, сохранённые раньше. В той же форме — блок «Паспорт» со страницы паспорта: номер, личный номер, гражданство, пол, даты выдачи и окончания, кем выдан, место рождения; хранится, как и раньше, в анкете клиента, а в карточке — отдельным блоком с кнопкой «Распознать паспорт». В шаблонах документов — коды `{{Фамилия}}`, `{{Имя}}`, `{{Отчество}}`, `{{Фамилия латиницей}}`, `{{Имя латиницей}}`, `{{Кем выдан паспорт}}`, `{{Место рождения}}`. В журнал — названия изменённых полей, в том числе паспортных, без значений.
- Консультация и анкета (2026-10-16): ответы анкеты (паспорт, визы за 5 лет, отказы, родственники за границей, депортация, гуманитарные поездки) хранятся в контакте, а не в консультации, — при повторном обращении их не переспрашивают. Проверки анкеты только предупреждают и берут правила из справочника стран: срок паспорта задаётся у страны (для Шенгена — выдан не более 10 лет назад и действует ещё 3 месяца после выезда, Шенгенский кодекс о границах, ст. 6); для стран без правила проверки нет. Проверка идёт по странам и дате поездки последней консультации; без даты поездки — от сегодняшнего дня. Оплата консультации — сумма и валюта из валют, которые принимает визовик; пересчёт в BYN — вместе с платежами (1.9). «Создать кейс» — вместе с кейсами (1.4).
- Кейс (2026-10-16): кейс — одна виза одного заявителя, у каждого члена семьи своя карточка контакта и свой кейс; номер кейса сквозной у визовика (№1, №2, …). Поля: страна визы, цель, где подаётся (страна подачи и город — визовый центр из правила «страна визы × страна подачи» справочника), регистратор и зал, дата подачи, этап и результат. Этапы: ожидание записи → сбор документов → подача → рассмотрение → результат. Кейс переходит дальше сам, когда внесена дата подачи (ожидание → сбор документов) или результат (→ результат); назад сам не возвращается, остальные переходы визовик делает вручную на шкале этапов (в «Результат» — только с итогом, с 2026-11-18: → «Аудит по скиллу crm-management»). Результат — итог (виза / отказ / не подавался), тип визы, срок действия, дней пребывания, «после апелляции» и дата решения; поля, которые к итогу не относятся, очищаются. Срок апелляции при отказе считается от даты решения по сроку из справочника (там, где консульство принимает апелляции). Отказ из кейса учитывается в проверках анкеты, как отказ из анкеты: новый кейс в ту же страну получит предупреждение.

- Прибыль по месяцу оплаты (2026-10-26, ответ визовика на вопрос 18): визовик считает прибыльность в том месяце, когда пришли деньги, а не когда кейс подан. По некоторым направлениям работа начинается с предоплаты (позже — и с оплаты консультации), остаток клиент платит по факту записи: клиента поставили в очередь — он оплатил — визовик отправляет талон и список документов, и они готовятся к раздаче. Между предоплатой и записью проходят от пары недель до нескольких месяцев. Поэтому прибыль по месяцам и за период в «Аналитике» считается по датам оплат клиента (платежи кейса и оплата консультации); подачи, выдачи и одобрение остаются по дню подачи, каналы и партнёры — по консультациям периода. Как делить прибыль кейса между месяцами, когда оплат несколько, — вопрос 25. До ответа и задачи 1.18 отчёт считает по месяцу подачи. Уточнение владельца (2026-10-28): прибыль считается только по кейсам. Оплата консультации входит в прибыль, только когда она засчитана в стоимость кейса (тогда — в месяце оплаты консультации); консультация, после которой кейс не открыли, в прибыль не входит. Задача 1.18 ждёт ответа на вопрос 25 — без него не начинаем.
- Расходы по каналам и выгрузка (2026-10-26, ответы визовика на вопросы 5–7): плана на месяц визовик не ставит; аналитикой смотрит число клиентов, каналы прихода и прибыльность. Рекламы пока нет — рабочий Instagram она ведёт сама. Расходы по каналам позже понадобятся, чтобы видеть затратность и прибыльность каждого канала, — эпик 4.8: расход канала за месяц, стоимость клиента и прибыль канала за вычетом расходов в «Аналитике». Выгрузка в Excel нужна — эпик 4.9: отчёты «Аналитики» и платежи за месяц, в том числе официальные для налога. Оба эпика — в этапе 4 «Коммуникации и финансы».
- Импорт таблиц (2026-10-17): визовик запускает сам — только владелец кабинета, не сотрудник. Файл — XLSX (выгрузка из Google Таблиц со всеми листами, лист выбирается) или CSV (запятая или точка с запятой, UTF-8 или Windows-1251), до 5 МБ и 5000 строк; файл не хранится, браузер отправляет его заново для проверки и загрузки. Пять видов таблиц: консультации, клиенты в работе, очередь одной страны, заявки с окном одной страны, брони. Заголовки — первая строка с двумя заполненными ячейками или указанная вручную. Колонки сопоставляются с полями по привычным названиям; сопоставление и выбор для незнакомых значений запоминаются по виду таблицы, страна таблицы угадывается по названию листа или файла. «Проверить» — тот же импорт без записи: что будет создано и обновлено, пропущенные строки и предупреждения (номер строки и заголовок колонки, без значений) и незнакомые значения списков: канал, партнёр, цель, регистратор — добавить в список (по умолчанию; регистратор — частное лицо в базовой валюте), взять существующий или не заполнять; страну — выбрать или не заполнять; город подачи — только из справочника центров. Человек находится по телефону, затем по Telegram, затем по ФИО (порядок слов, регистр и «ё» не важны), если такая карточка одна и у неё нет другого телефона или ника; иначе создаётся новая карточка. Местные белорусские номера (8 029…, 029…, 29…) читаются как +375. Строка запоминает, во что превратилась (ключ — вид и страна таблицы, ФИО, для «Клиентов в работе» — страна кейса, и номер такой строки по порядку), и при повторной загрузке обновляет те же записи. Пустая ячейка ничего не стирает; карточка клиента только дополняется, а консультация, кейс, запись в очередь, заявка и бронь берут значения таблицы. Новая строка подхватывает введённое вручную: консультацию того же дня, кейс клиента в той же стране (открытый и новый — первым), запись в очередь с той же датой или открытую. Кейс из таблицы открывается из последней консультации клиента, «думает» становится «да», как при открытии кейса вручную, и повторная загрузка консультаций это «да» не меняет. Дата создания кейса — самая ранняя известная (консультация, постановка, заявка, подача), этап — по данным: результат → «Результат», подача прошла → «Рассмотрение», впереди → «Сбор документов», иначе «Ожидание». Результат словами («мульти на 2 года», «отказ», «после апелляции», «не подались») раскладывается на исход, кратность и апелляцию, нераспознанный — предупреждение. Стоимость и «оплачено» — только в базовой валюте (сумма в другой валюте — предупреждение, её вводят вручную с курсом); оплата — один платёж на дату оплаты, иначе подачи, иначе загрузки. Оплата консультации — в своей валюте; сумма в колонке значит «оплачено», если колонка «оплачено» не говорит иного. Пароли уходят в сейф зашифрованными, в выбранную систему (почта, сайт ВЦ); в примерах колонки с паролями скрыты, после загрузки — напоминание удалить пароли из Google Таблиц. Заявка с окном: номер — повторы + 1, 60-й день — из таблицы или по окну страны. Бронь — в кейс клиента (страны из строки, иначе последний открытый), без кейса строка пропускается; аккаунт Booking — по логину из сейфа. Семьи в группы подачи импорт не объединяет (вопрос 19). В журнал — одно событие на загрузку с количествами, без данных клиентов. Около 2000 строк «Клиентов в работе» загружаются примерно за 20 секунд, повторная загрузка без изменений — за пару секунд.
- Импорт под таблицы визовика (2026-10-18, 1.16; сверка с описанием таблиц от владельца): у каждого визовика таблицы свои, поэтому импорт остаётся универсальным — сопоставление колонок запоминается для каждого визовика, колонка без заголовка — по её месту; ИИ-подсказка сопоставления (заголовки и обезличенные примеры, визовик подтверждает) — позже, отдельной задачей. Ключ строки включает имя листа (для CSV/TSV — имя файла без « (1)»): строки одного человека из листов разных лет — разные кейсы. «-», «—», «нет» и 0 в сумме — пустая ячейка; строки только из нулей и прочерков не считаются. Пометки после ФИО — «(коллега Анны)», «от Ольги Т.» — уходят в заметку карточки, человек ищется по чистому имени; «(повторно)» отбрасывается. Несколько человек в одной ячейке («А + супруга + сын», «А и Б») — одна карточка с предупреждением (вопрос 19); бронь такой строки — в кейс первого найденного. По Telegram люди склеиваются только по нику, свободный текст («в вайбере») никого не склеивает. Даты: дни Excel (лист, сохранённый как текст), «17.12 2026», «до 25.12.2026»; с предупреждением о догадке — «17.08» (год из названия листа, иначе текущий), «октябрь 2024» (1-е число), консультация без даты — 1-е число «Месяца обращения»; один год — не дата. Дата рождения в будущем или до 1910 года не переносится. Регистратор «я», «самостоятельно», «я помогала», «без посредника» — регистратора нет. Талоны из таблиц («Оплата за талон», «Мой расходник», «Оплата моя посредникам» — вопрос 20) — решение владельца 18.10.2026: импортируются как уже оплаченные регистраторам — в прибыли кейса есть, долга в расчётах с регистраторами не создают (отметка «оплачен до CRM» в финансах кейса, её можно снять, и талон войдёт в расчёты); талон без регистратора не переносится, талон, введённый в CRM, импорт не меняет. Выплаты партнёрам из таблиц («Оплата процента») — по аналогии с талонами: фиксированная сумма, уже выплаченная (в день решения, иначе подачи, иначе загрузки), чтобы на главной не висел долг партнёрам за прошлые годы; условия партнёра, заданные в CRM, импорт не меняет. Незнакомое значение «Откуда» можно сделать партнёром, а не каналом; два написания одного регистратора объединяются («Как «…»»). «почта пароль» в одной ячейке: почта — логин, остальное — пароль в сейф, никуда больше; почта, созданная визовиком («email создала я»), — учётная запись с отметкой «создала сама» и почта заявки; в примерах колонок скрыты колонки «пароль», «кабинет», «логин» и ячейки вида «почта пароль». Франция: «Повторно» — следующая заявка, прежняя закрывается истёкшей на свой 60-й день, «не ставим» — последняя отменяется. Италия: «Дата постановки в очередь в новом ВЦ» — вторая запись в очереди, первая закрывается этим днём. Комментарий очереди «Удалена из очереди 12.06.2026» снимает с очереди, остальные комментарии — в заметку карточки. Дата постановки из «Клиентов в работе» становится записью в очередь, только если у страны лист ожидания. Кейс из таблицы связывается с последней консультацией не позже своей первой даты. Код пользователя Греции — номер кейса в ВЦ (идентификатор Греции по справочнику — имя пользователя). Лист «Почты» пока не загружается: нужен свой вид импорта.
- Формат данных VisaCRM (2026-10-27, решение владельца, 1.21): импорт с сопоставлением колонок и правилами чтения под таблицы одного визовика (1.14, 1.16 — две записи выше) заменяется полностью одним форматом на вход и на выход — [data-format.md](data-format.md). Таблицы у каждого визовика свои, и на этапе SaaS дописывать правила чтения под каждого нельзя: свои таблицы в формат переводит ИИ по универсальному промту ([import-prompt.md](import-prompt.md)), а CRM принимает только строгий формат и не угадывает. Файл — XLSX: открывается в Excel, Google Таблицах и LibreOffice, держит несколько листов, настоящие даты и суммы, выпадающие списки; CSV и JSON не принимаются. Листы: клиенты, заметки, консультации, кейсы, платежи, расходы, очередь, заявки с окном, брони, учётные записи; в выгрузке и шаблоне ещё «Справочник» и «О файле». Листы связаны кодами; в выгрузке коды — внутренние идентификаторы CRM, чтобы строка из файла ИИ не попала в чужую запись. Повторная загрузка узнаёт запись по коду CRM, иначе по содержимому; пустая ячейка в файле ИИ ничего не меняет, а в строке из выгрузки очищает поле; строку записи, изменённой в CRM после выгрузки, импорт не загружает; строка, убранная из файла, ничего не удаляет. Семью задаёт колонка «Семья» (код группы подачи), лист «Почты» становится учётными записями без клиента. Расходы и заметки — в версии 1; прибыли и налога кейса в файле нет. Делается до пилота: таблицы пилота переносятся через промт и формат.
- Промт для перевода таблиц (2026-10-27, решение владельца, 1.21): универсальный промт ([import-prompt.md](import-prompt.md)) работает в двух режимах, и ИИ в начале спрашивает визовика, какой выбрать. Режим 1 — таблицы целиком, без колонок с паролями: файл импорта собирает сам ИИ. Режим 2 — ИИ видит только заголовки и несколько строк с изменёнными данными и пишет скрипт Google Apps Script; визовик запускает его у себя, и данные клиентов с паролями не покидают Google Таблицы. В режиме 1 данные клиентов уходят компании, которая делает ИИ, часто за пределы Беларуси и ЕС; за это отвечает визовик, и об этом сказано в инструкции к промту. ИИ работает кодом, ничего не придумывает и не теряет молча, сначала разбирает листы и задаёт вопросы, потом переводит; правила чтения ячеек из 1.16 перенесены в промт. В CRM промт — на странице импорта, на русском и английском; список листов и колонок в нём совпадает с data-format.md.

- Карточки до загрузки (2026-10-30, решение владельца, 1.22): файл от ИИ не попадает в картотеку сразу. Визовик загружает его один раз, и он ждёт на сервере, пока она не подтвердит загрузку или не отменит её. Сначала CRM показывает пробные карточки — пять первых клиентов файла со всем, что к ним относится по кодам, такими, какими они станут в CRM. Всё верно — обрабатывается весь файл с полосой хода, без записи. Затем визовик открывает любую карточку из файла: поля формата с заголовками колонок, отметки «новая / изменится / без изменений» у карточки и «новое / изменится» у записей, замечания по строкам этого клиента; пароль — только «есть». После этого она подтверждает загрузку — весь файл целиком; загрузка без проверки не начинается. Отдельные карточки не исключаются и на месте не правятся: нашла ошибку — «Отменить», исправить файл с ИИ и загрузить снова. Подтверждение загружает тот же файл заново; если данные в CRM за это время поменялись, итоговый отчёт покажет, что загрузилось на самом деле. - Сортировка таблиц (2026-11-18, решение владельца по итогам UI/UX-аудита 17.11.2026): таблицы, по которым визовик ищет или сравнивает, сортируются нажатием на заголовок колонки. Отчёты аналитики — каналы и партнёры, страны, визовые центры, очереди — по своим числовым колонкам; месяцы остаются рядом по времени. Не сортируются короткие или упорядоченные по смыслу таблицы: регистраторы (балансы в разных валютах) и лента регистратора (остаток после каждой строки), сотрудники, направления, «Ближайшие подачи», показанные пароли, импорт, шаблоны, финансы кейса и админские таблицы.

- Калькулятор 90/180 (2026-10-17): правило — не больше 90 дней в любые 180 (Шенгенский кодекс о границах, Регламент (ЕС) 2016/399, ст. 6); для каждого дня пребывания период — этот день и 179 дней до него, день въезда и день выезда считаются. Поэтому «сколько ещё можно» — не «90 минус использованные»: старые дни выпадают из периода прямо во время поездки, и система проверяет каждый день. Поездки хранятся в карточке клиента, а не в кейсе: дни человека в Шенгене не зависят от визы, по которой он ехал. У поездки — страна, въезд, выезд (пусто — «ещё там», дни считаются по сегодня), отметка «по визе D или ВНЖ» (такие дни не в счёт) и заметка. В счёт идут только страны Шенгенской зоны, и только с даты вступления: она хранится в справочнике стран («В Шенгене с», правит админ; Болгария и Румыния — с 31.03.2024, Хорватия — с 01.01.2023; Кипр и Ирландия не в зоне — когда Кипр вступит, админ поставит дату). В справочник добавлены Исландия, Лихтенштейн, Норвегия и Швейцария. Показывается: дни за последние 180, до какого дня можно оставаться (или выехать, если человек там), ближайший день въезда, с какого дня доступны полные 90, превышения — в прошлом (консульство может учесть их при новой подаче) и в запланированных поездках. Будущую поездку можно проверить без сохранения: укладывается ли, до какого дня можно пробыть и с какой даты поездка такой длины поместится. Страница «Калькулятор 90/180» считает любые даты и ничего не сохраняет — для консультации, когда клиента ещё нет. Ограничения ввода: даты с 1990 года и не дальше двух лет вперёд, поездка без отметки D/ВНЖ — не длиннее года, у будущей поездки обязателен выезд. Модуль «Калькулятор 90/180» (этап 2) новому визовику не включён — админ включает в «Настроить»; блок в карточке виден с модулями «Клиенты» и «Калькулятор». Поездки пишутся в журнал только идентификаторами. Расчёт — `app/core/stay.py` с юнит-тестами.
- Распознавание паспорта (2026-10-17): фото страницы паспорта читается прямо в браузере (движок Tesseract в WebAssembly и английская модель отдаются с нашего же сайта, без CDN, и загружаются, только когда визовик распознаёт фото: около 4 МБ движка и 3 МБ модели). Само фото не уходит на сервер и нигде не хранится — так решение «сканы не храним» выполняется строже, чем при разборе на сервере. На сервер отправляются только строки машиночитаемой зоны (их можно и ввести вручную, например скопировав текст с фото на телефоне); сервер разбирает их по ICAO 9303 (паспорт — 2 строки по 44, ID-карта — 3 по 30 или 2 по 36), проверяет контрольные цифры, а похожие символы исправляет по типу поля (цифры в датах, буквы в кодах стран; в номере паспорта — только если с заменой сходится контрольная цифра). Визовик видит распознанное рядом с тем, что уже есть в карточке, и сам отмечает, что перенести; при несошедшихся контрольных цифрах ничего не отмечено заранее. Паспорт хранится в анкете клиента рядом с датами выдачи и срока: номер, гражданство, пол и личный (идентификационный) номер — для визовых анкет (2.4); перенос пишется в журнал как изменение карточки, без значений (с 2026-10-24 паспорт — отдельный блок карточки, см. «ФИО по частям и паспорт в карточке»). Чтобы браузер мог запустить движок, в политику безопасности добавлено `'wasm-unsafe-eval'` — разрешает только WebAssembly, но не `eval`. Модуль «Распознавание паспорта» новому визовику не включён — админ включает в «Настроить». Разбор — `app/core/mrz.py` с юнит-тестами, чтение фото — `frontend/src/ocr.ts`. С 2026-10-27 (белорусский паспорт с фото не находился): длинный хвост из `<` в строке имени распознавание считает неточно и часть знаков читает как C, K или L. Поэтому строка имени любой длины принимается, если в ней есть двойной `<` после фамилии: её обрезают или дополняют до длины строки данных, которая и служит опорой. Строку имени точной длины ищут первой, иначе шум с `<<` над зоной занял бы её место. Хвост из C, K, L после имени считается заполнителем. Личный номер белорусского паспорта читается по его маске — 7 цифр, буква, 3 цифры, 2 буквы, цифра, — как даты: по типу поля, без угадывания. Подбирать замену похожего символа по контрольной цифре в личном номере не стали: на 14 знаках неверная замена слишком часто тоже сходится с контрольными цифрами. В браузере то же фото читалось хуже, чем самим движком: наш перевод в оттенки серого терял первые символы строки данных. Поэтому фото отдаётся движку в цвете (серые цвета он делает сам), и читается оно несколькими способами по очереди: нижняя половина, нижняя треть, половина в оттенках серого, всё фото, перевёрнутое и на боку. Каждый способ ошибается в разных символах, поэтому строки каждого сразу проверяет сервер. Берётся первый результат, где сходятся все контрольные цифры, иначе тот, где не сошлось меньше всего. На сервер по-прежнему уходят только строки зоны. Строка данных паспорта, в которой потерялись или добавились до 4 знаков, читается с конца: гражданство, даты, пол и личный номер стоят на своих местах, а номер паспорта показывается как прочитан и всегда помечается как несошедшийся — при сдвинутом номере совпадение контрольной цифры было бы случайным. Лишние знаки перед кодом страны в строке имени (`FPEBLR` вместо `P<BLR`) отбрасываются, если сразу за ними стоит код гражданства из строки данных.
- Чек-листы документов (2026-10-17): список документов ведётся по стране визы. Общий список ведёт админ в справочнике («Страны и правила» → «Чек-листы»), он одинаковый у всех визовиков; визовик не меняет его, а добавляет свои пункты поверх (страница «Чек-листы документов»). У пункта — название, «обязательный» или «по ситуации» (зависит от заявителя: например, справка с работы — для работающих), срок свежести в днях к дате подачи (пусто — без ограничения), требования и когда нужен (текст), для каких целей (пусто — для любой) и страна подачи (пусто — любая; например, вид на жительство при подаче в Турции). Цели у каждого визовика свои, поэтому общий список идёт по типу цели — общему для платформы списку по шенгенской анкете (туризм, гости, деловая поездка, учёба, культура, спорт, официальный визит, лечение, транзит, другое) плюс работа; визовик задаёт тип своим целям в «Справочниках» (стартовые цели получают его сами). Цель без типа получает только пункты для любой цели. Отдельного поля «тип визы» (C или D) нет: у визовика это разные цели (туризм — C, работа — D), а пункты подбираются по цели. Пункты не удаляются, а выключаются: на них будут ссылаться кейсы (проверка пакета, 2.3). Список можно сузить до кейса — страна подачи и цель — и увидеть то, что получит проверка пакета. Названия пунктов — на одном языке (как ввёл админ). Всё это — модуль «Проверка пакета» (этап 2, админ включает); правило подбора — `app/core/checklists.py` с юнит-тестами. Наполнение общего списка ждёт списков визовика (М3) или сверки с сайтами консульств — сам список не придумываем; на стенде есть демо-список для Польши.
- Шаблоны документов (2026-10-18, решение владельца): у каждого визовика свои шаблоны, и все они разные, поэтому общих шаблонов админа пока нет. Шаблон — файл Word (.docx), в который визовик сама вставляет коды в двойных фигурных скобках вместо данных клиента: `{{ФИО}}`, `{{Дата рождения}}`, `{{Номер паспорта}}`, `{{Страна визы}}`, `{{Стоимость}}`, `{{Сегодня}}` и другие — список с инструкцией на странице «Шаблоны документов». Код пишется по-русски или по-английски, регистр, пробелы и подчёркивания не важны; язык кода — язык значения там, где есть выбор («Беларусь» или «Belarus», запись суммы). Значения — в начальной форме, без склонения; даты — 05.10.1990. Код только заменяется текстом — никаких условий, циклов и выражений, поэтому загруженный файл ничего не может выполнить; файлы с макросами, .doc и .dotx не принимаются, до 5 МБ. Незнакомый код (опечатка) показывается при загрузке и остаётся в документе как есть, чтобы его было видно. Визовик загружает шаблоны в свой список (только владелец кабинета; сотрудник с модулем видит список, добавляет шаблоны клиентам и скачивает). В карточке клиента шаблон добавляется клиенту — для одного из его кейсов (коды кейса берутся из него) или без кейса. Заполненный файл собирается при каждом скачивании из данных на этот момент и нигде не хранится — хранится только сам шаблон, зашифрованный ключом визовика, в том же S3-хранилище, что и согласия (ключ `templates/<визовик>/<шаблон>`); каждое скачивание — в журнале, с идентификаторами без имён. Имя файла — по правилу шаблона с кодами (например, «Спонсорское письмо {{ФИО}}») или «Название — ФИО клиента». Коды кейса видны только с модулем «Кейсы», суммы — только с «Финансами»: документ не показывает больше, чем карточка. PDF не делаем: для него нужен LibreOffice в образе (сотни мегабайт); визовик сохраняет PDF из Word сама. Коды — `app/core/templates.py`, подстановка — `app/core/docx_fill.py`, оба с юнит-тестами. Модуль «Шаблоны документов» (этап 2, админ включает).
- Пределы шаблона документа (2026-11-22, аудит безопасности, находки M3, M4, N11, задача S4): в шаблоне не больше 1000 кодов — считается каждый написанный код в тексте, колонтитулах и сносках вместе; больше — загрузка и замена файла отклоняются как слишком большой файл (413). В обычном письме кодов десятки, а каждый код — работа при каждой выгрузке. Части с текстом вместе со списком частей — не больше 300 000 узлов XML: несколько КБ архива из крошечных элементов разворачиваются в памяти в сотни МБ, а 300 000 узлов — это около 5 МБ разметки Word, сотни страниц, и не больше 40–120 МБ памяти на разбор. Член архива распаковывается кусками по 64 КиБ и не дальше заявленного размера; принимаются только способы сжатия, которыми пишет Word (без сжатия и deflate), остальное — «Файл повреждён» (422). Так же отклоняются архив с двумя частями одного имени и DTD в любой части. Разбор и заполнение идут в отдельном потоке, а не в общем цикле событий; заполнение линейно по числу кодов, поэтому шаблон, загруженный раньше с большим числом кодов, по-прежнему выгружается. Код — `app/core/docx_fill.py`.
- Проверка пакета (2026-10-25, 2.3): у каждого пункта чек-листа кейса визовик отмечает «есть / нет / не нужно» и дату документа; статус пункта считается, а не хранится (`app/core/package.py`). Не отмечен или «нет» — не хватает; «есть» без даты при сроке свежести — нет даты; старше срока к дате подачи — просрочен (документ ровно N-дневной давности при сроке N дней ещё годен). Пока у кейса нет даты подачи, срок свежести считается на сегодня (в часовом поясе визовика), и система показывает, от какой даты считала. Дата документа не может быть позже сегодняшней (по поясу визовика): иначе опечатка в годе выдала бы старую справку за свежую. Пакет готов, когда среди обязательных пунктов нет «не хватает», «нет даты» и «просрочен»; пункты «по ситуации» подсвечиваются, но готовность не держат. Выключенный пункт пропадает из пакета, отметка по нему остаётся и вернётся, если пункт включат снова. Часть 1 — правило и API; блок в кейсе, «Требует внимания» и главная — следующими частями. _Часть 2 (2026-10-27): в карточке кейса — блок «Документы»: одна строка «Пакет собран» или «Не хватает: N» (N — обязательные пункты, которые держат пакет) и от какой даты считали, чек-лист раскрывается кнопкой; отметка сохраняется сразу, дата — когда поле покинули. Для страны и цели без чек-листа — строка со ссылкой на «Чек-листы документов». В «Требует внимания» — «Не собраны документы к подаче»: за 7 дней до подачи и накануне, пока пакет не готов, до дня подачи; окно визовик меняет в «Справочниках» → «Напоминания» (по умолчанию 7 дней, пока нет ответа на вопрос 26). На главной в «Ближайших подачах» вместо этапа — готовность документов; у семьи — по всем её кейсам. Кейс без чек-листа ни в напоминания, ни в готовность не попадает: на главной у него остаётся этап. Всё это — только с модулем «Проверка пакета»; сотрудник видит пакет лишь своих кейсов._
- Цель визы в анкете и понятный калькулятор (2026-11-13, отзыв визовика после пробы): у визы в анкете консультации есть поле «Цель». Оно берётся из общих целей платформы (`PurposeKind`, те же слова, что у чек-листов), а не из справочника визовика: цели сравнимы у всех, а анкета хранится как JSON, поэтому миграция не нужна — у виз, внесённых раньше, цели просто нет. Тип визы (Шенген, национальная…) остался: он отвечает на вопрос «какая», цель — «зачем ездил». Визы, отказы и депортация в карточке показаны построчно: страна, тип, цель, срок и метка «действует / истекла» (по дате в часовом поясе визовика), а не одной строкой через «;». Калькулятор 90/180 считает по тем же правилам, меняется только экран (образцы — visa-calculator.com и visa-pro.com.ua): ответ стоит рядом с вводом и виден, пока вводят даты; под каждой поездкой — её итог (сколько дней и сколько из 90 было в периоде на выезде); рядом с «использовано» — «свободно N дн.» и пояснение, почему остаться можно дольше этих дней (период сдвигается каждый день); проверка поездки отвечает вердиктом и цифрами под ним, по пункту на строку. Итог строки сопоставляется с поездкой по ключу строки, а не по номеру: пока приходит новый ответ, старый не переезжает на другую поездку при добавлении и удалении строк. Режим «контрольная дата» (счёт на любой день, а не только на сегодня, как у visa-pro) не делали: будущая поездка проверяется отдельной формой. Поездки в карточке — список блоков (страна и действия, въезд, выезд, дни, заполнение периода), а не таблица: колонка карточки узкая.
- Что визовик готовит сама (2026-10-26, ответ визовика на вопрос 2): набор свой у каждой страны и цели — где-то только анкету, где-то анкету и брони, где-то анкету, брони, маршрутный лист, сопроводительное и спонсорское письма и переводы. Всего она делает: анкеты, брони отелей, автобусные билеты, авиабронь, маршрутный лист, сопроводительное письмо, спонсорское письмо, переводы на иностранный язык, апелляции. В CRM: анкеты — данные для анкет (2.4; начинаем с шенгенской, другие страны — вопрос 22); брони отелей — брони кейса (1.8); сопроводительное и спонсорское письма, маршрутный лист и апелляции — её шаблоны документов (2.1); переводы и черновики писем — AI-помощник (2.7). Авиабронь (в CRM её делает и оплачивает клиент) и автобусные билеты (вида брони для них нет) — вопросы 23 и 24.

- Налог: 10% от официально оплаченных платежей (НПД); ставка — настройка визовика.
- Авиабронь делает и оплачивает клиент — это не расход визовика; в кейсе хранится только её срок действия. _Авиабронь есть в списке того, что визовик делает сама (вопрос 2), — кто её оплачивает, вопрос 23._
- Страховка (2026-10-26, ответ визовика на вопрос 1): визовик страховку не оформляет — на ней нужны подписи и печати в оригинале, а сама она не в Беларуси. Страховку клиент оформляет сам: в финансах кейса её нет ни доходом, ни расходом, в пакете документов она — обычный пункт чек-листа страны (2.2).
- Прибыль = стоимость − талон − выплата партнёру − налог − прочие расходы.
- Валюта учёта и налог — настройки каждого визовика (для SaaS, к этапу 3).

- T2. Консультация и кейс (правки 2 и 8; решение владельца 2026-11-19). Кейс, открытый из консультации одного клиента на другого (пришла дочь, кейс на отца), связан с ней в интерфейсе с обеих сторон: в консультации — список открытых из неё кейсов с заявителями, в кейсе — консультация-источник с датой и чьей она была. Финансы кейса (правки 4 и 5, решения владельца 2026-11-19). **Валюта стоимости у кейса**: визовик выбирает её из принимаемых валют кабинета (базовая — по умолчанию); в ней стоимость, предоплата, зачёт консультации и остаток. Кейс хранит валюту и курс к базовой (`case_finances.currency`, `rate` — единиц базовой за единицу, миграция 0040; старые кейсы получили базовую валюту кабинета и курс 1). Курс — последний курс Нацбанка на сайте (через BYN), его можно поправить; меняется только при смене валюты или вручную. Платёж в валюте кейса идёт в остаток как есть, в другой валюте — суммой в базовой, делённой на курс кейса; остаток округляется один раз. Налог, талон, выплата партнёру (процент — от стоимости в базовой), расходы и прибыль — в базовой валюте; аналитика и долг клиентов на главной сводят всё в базовую. **Платёж клиента — доход**: в финансах кейса он показан без минуса, в валюте кейса; у каждой суммы подписана валюта, заголовок — просто «Финансы». **Ставка налога не задана** (0 — значение по умолчанию нового кабинета): вместо «Налог 0% … 0» — «Налог: ставка не задана» и подсказка, что ставку задаёт администратор; налог не считается, прибыль — без него. **Без стоимости** остаток и прибыль не считаются: вместо «—» подсказка «укажите стоимость», в аналитику такой кейс не входит, долга не даёт. Причины на пилоте: минус перед платежом рисовала страница (платёж «вычитался» из стоимости), налог 0% — ставка кабинета не задана (её задаёт админ, не визовик), «минус» в прибыли и остатке — базовая валюта PLN при стоимости, которую визовик называла в BYN (300 «PLN» − 402,70 PLN платежей = −102,70). Пересчёт 150 BYN по 1,341598 = 201,24 PLN верен: курс — злотых за рубль (Нацбанк: 10 PLN ≈ 7,45 BYN). Формат XLSX валюты стоимости не получил: стоимость в файле — в базовой валюте, как и раньше; у кейса в другой валюте карточки до загрузки показывают её пересчитанной в базовую, а файл, где стоимость та же, валюту кейса не меняет (иначе кейс возвращается в базовую валюту). Нужна ли в формате колонка «Валюта стоимости» — открытый вопрос владельцу.

- T8. **Смена валюты учёта при внесённых данных.** Платёж, расход и талон сохраняют свою сумму и валюту, пересчитывается только сумма в базовой валюте: из исходной суммы и валюты по последнему курсу Нацбанка на сайте, через BYN (`app/core/base_currency.py`, курс — `rates.cross_rate`); у строки уже в новой валюте курс 1. Курс, поправленный вручную, был к старой валюте, поэтому его заменяет курс банка, и визовик может поправить его снова. Стоимость кейса остаётся в валюте кейса (T5), пересчитывается курс кейса к новой валюте учёта (кейс в ней — курс 1). Фиксированная выплата партнёру в кейсе (`partner_fixed`) хранится в базовой валюте без своей валюты, поэтому переводится из старой валюты учёта в новую с округлением один раз; меньше 0,01 она не становится (0,01 BYN — это 0,003 USD, а выплата 0 читалась бы как «платить нечего»). Не трогаются суммы со своей валютой: подписка (валюта платформы), оплаты и прайс регистраторов и порог их аванса, условия партнёров, оплата консультации, предоплаты справочника (см. ниже). Старая валюта учёта остаётся среди принимаемых. Всё идёт одной транзакцией с одной записью журнала `workspace.base_currency_changed` (коды валют и число строк каждого вида). Если на сайте нет курса нужной валюты — отказ `base_rate_unavailable`, ничего не меняется; во время загрузки файла — `import_running`; образец или проверка файла останавливаются (они считали в старой валюте). Перед сменой страница спрашивает ещё раз, что будет пересчитано, с фокусом на «Отмене».
- T8. **Платёж во время смены валюты учёта** (ревью 2026-11-20). Запись, которая считает сумму в базовой валюте, — платёж, расход, талон (в финансах кейса и в расчётах с регистратором), курс кейса, загрузка файла — сначала берёт строку кабинета `FOR KEY SHARE` и держит её до конца транзакции (`hold_base` в `app/core/base_currency.py`). Смена валюты учёта берёт ту же строку `FOR UPDATE`: она ждёт записи, которые уже идут, и пересчитывает и их строки, а запись, пришедшая во время смены, ждёт её конца и читает новую валюту, — курса к старой валюте не остаётся. `FOR KEY SHARE`, а не `FOR SHARE`: обычное изменение строки кабинета (ставка налога, принимаемые валюты, напоминания — `UPDATE`, то есть `FOR NO KEY UPDATE`) с ним не конфликтует и не ждёт ни платежей, ни долгой загрузки файла. Сохранение настроек «Валюта учёта и налог» и у админа берёт строку `FOR NO KEY UPDATE` (одно изменение настроек за раз), а `FOR UPDATE` — только сама смена валюты, после остановки образца и проверки файла. Тест — `test_a_payment_saved_during_a_change_waits_and_takes_the_new_base`.
