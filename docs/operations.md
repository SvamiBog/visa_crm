# Эксплуатация

Команды запускаются в каталоге `backend`: локально — `uv run python -m app.cli <команда>`, на Railway — в оболочке веб-сервиса (`railway ssh`, затем `cd /srv/backend`) через `python -m app.cli <команда>`, без `uv run`. Как выложить сервис — docs/deploy.md.

## Первый администратор

```bash
uv run python -m app.cli create-admin you@example.com   # спросит пароль дважды
```

Регистрации на сайте нет: визовиков создаёт админ в админ-панели.

## Двухфакторный вход: потерян телефон

- **Визовик.** Админ в панели «Визовики» нажимает «Новый пароль»: выдаётся временный пароль, двухфакторный вход сбрасывается; включить его снова визовик может в «Настройках».
- **Админ.** На сервере:
  ```bash
  uv run python -m app.cli reset-two-factor admin@example.com
  ```
  Все сессии этого пользователя закрываются; при следующем входе он подключает приложение заново.

## Коды восстановления и `SECRET_KEY`

Коды восстановления двухфакторного входа хранятся как HMAC с ключом, выведенным из `SECRET_KEY` (`backend/app/core/two_factor.py`). Без этой переменной копия базы бесполезна для подбора кодов.

- `SECRET_KEY` — случайная строка не короче 32 символов, своя у production и staging. Сгенерировать можно так: `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Хранится в Variables сервиса и в менеджере паролей владельца.
- Везде, кроме локальной разработки и тестов, пустой `SECRET_KEY`, `change-me` и ключ короче 32 символов не принимаются: сайт не запускается, в логе выкладки `InvalidSettings: SECRET_KEY must be at least 32 random characters…` (backlog S19, docs/deploy.md, шаг 4).
- Сменить `SECRET_KEY` — значит сделать недействительными все выданные коды восстановления: старый код становится просто неверным кодом. Вход по коду из приложения работает. То же будет, если восстановить базу на окружение с другим `SECRET_KEY`. Поэтому ключ меняют только при утечке, вместе с полной сменой ключей (ниже), которая и так удаляет все коды.
- Если ключ всё же сменили (по ошибке или при восстановлении), верните прежнее значение, если оно сохранилось: коды снова заработают. Если прежнего нет, каждому, у кого включён двухфакторный вход, нужно выключить и снова включить его в «Настройках» (для выключения хватает кода из приложения): так он получит новые коды. Тому, кто потерял ещё и телефон, двухфакторный вход сбрасывают как при потере телефона (раздел выше): визовику — админ кнопкой «Новый пароль», сотруднику — визовик, выдав ему новый временный пароль, админу — команда `reset-two-factor`.
- Коды, выданные до перехода на HMAC (backlog S16), хранились как SHA-256 без соли. Они продолжают работать и переводятся в новый вид при первом использовании. Один раз после выкладки переведите все сразу, чтобы в базе не осталось хешей, которые можно перебрать:
  ```bash
  uv run python -m app.cli upgrade-recovery-codes   # «Kept N recovery codes as HMAC»; повторный запуск — 0
  ```

## Демо-данные тестового стенда

```bash
uv run python -m app.cli seed-demo                     # 5 визовиков по ~300 клиентов
uv run python -m app.cli seed-demo --specialists 2 --clients 50
```

Только при `ENV` = `local`, `staging` или `test` и с переменной `DEMO_PASSWORD` (`DEMO_TOTP_SECRET` — по желанию: с ним у админа и визовиков демо включён двухфакторный вход); в production команда отказывается. На стенде запускается сама при старте (`SEED_DEMO=1`), повторный запуск ничего не дублирует. Подробно — docs/staging.md.

## Отчёты об ошибках (Sentry)

Ошибки сервера production и `staging` приходят в Sentry, если в сервисе задана `SENTRY_DSN` (настройка — docs/deploy.md, шаг 4 → «Отчёты об ошибках»). Код — `backend/app/core/error_reports.py`.

**Кто получает.** Владелец платформы: письмо на почту аккаунта Sentry о каждой новой ошибке. Повторы той же ошибки в том же месте собираются в одну задачу (issue) со счётчиком, нового письма не будет. Если исправленная ошибка вернулась после **Resolve**, Sentry напишет снова.

**Что приходит.** Сбой, на который сайт ответил 500; ответы 502 и 503 с кодом (`storage_failed`, `storage_unavailable`, `mail_failed`, `mail_unavailable`) — хранилище или почта не ответили; строки журнала уровня ERROR (например, импорт, который упал, или файл, который не расшифровался). Отказы по правилам (неверный пароль, 403, 404, 422, лимиты сотрудника) — не ошибки, их нет.

**Что смотреть в отчёте.**
- **Environment** — `production` или `staging`.
- **Release** — коммит выкладки: по нему видно, после какого PR началось.
- **Transaction** — обработчик, где упало, например `app.api.documents.download_document`. Пути с id в отчёте нет.
- Тип ошибки и кадры: файл, строка, функция и код вокруг строки.
- **Breadcrumbs** — предупреждения журнала перед ошибкой: шаблон строки, из значений только id и числа.

Текста ошибки в отчёте нет намеренно: он может процитировать значение поля (asyncpg и уникальные ключи так делают). Нет и данных запроса: тела, строки запроса, cookies, IP, кто вошёл. Если этого мало, ищите в журнале Railway строку в то же время: `POST app.api.… failed: DataError` с кадрами; в ней тоже нет значений. Что делал визовик, спросите у неё, данные клиента для этого не нужны.

**Проверка.** После смены DSN и раз в месяц, вместе с проверкой бэкапа (docs/backup.md):

```bash
python -m app.cli check-error-reports   # «Sent test report <id> (production)…»
```

В Sentry появится `ErrorReportCheck` с окружением сервиса и придёт письмо. Затем отметьте его **Resolve**. Если письма нет: переменная `SENTRY_DSN` на месте, Sentry не исчерпал месячный лимит событий тарифа (**Settings → Subscription**), письмо не ушло в спам.

**Если в отчёте видны данные клиента.** Это инцидент: удалите задачу в Sentry (**⋯ → Delete**), запишите, какое поле и в каком отчёте, и поправьте чистильщик в `error_reports.py` с тестом в `backend/tests/test_error_report_rules.py`. Что именно уходит и почему — decisions.md → «Отчёты об ошибках в Sentry».

## Удаление паспортных данных после решения

Сайт сам удаляет паспортные данные клиентов через неделю после решения по визе: при запуске и каждые 6 часов (задача 2.8, decisions.md → «Удаление паспортных данных после решения»). В логе — `Passport data removed after the decision: N clients`, ошибка — `Removing passport data failed: <тип>`; данных клиентов в логе нет. Запустить вручную (удаляет только то, что пора):

```bash
uv run python -m app.cli purge-passports
```

В production удаление выключено (решение владельца 24.11.2026, decisions.md): работает только на тестовых стендах. Включить — в переменных веб-сервиса production задать `PASSPORT_PURGE_FROM=<ГГГГ-ММ-ДД>`, день включения (сегодня или будущий, не прошедший), и сделать **Deploy**. С этого дня в «Требует внимания» появятся клиенты, которым уже пора удалить паспорт, а удалятся они не раньше этого дня + 14. Выключить снова — удалить переменную. Пока выключено, `purge-passports` ничего не удаляет.

## Мастер-ключ сейфа (`VAULT_MASTER_KEY`)

Мастер-ключ шифрует (AES-256-GCM) ключи визовиков и секреты двухфакторного входа. Каждый визовик получает свой случайный ключ данных при первом обращении к сейфу или первой загрузке файла; в базе этот ключ лежит только зашифрованным мастер-ключом (`tenants.vault_key_encrypted`). Ключом визовика шифруются пароли клиентов в сейфе, файлы согласий и договоров и шаблоны документов в хранилище. Поэтому выгрузка базы без мастер-ключа не раскрывает ни одного секрета, а секрет, скопированный в чужую строку, не расшифруется.

При ротации мастер-ключа ключ визовика остаётся прежним, меняется только его обёртка, и файлы в хранилище не перешифровываются. Отсюда следствие: у кого есть старый мастер-ключ и любая копия базы до ротации (выгрузка, снимок, бэкап), тот достанет из неё ключи визовиков и прочитает пароли и файлы, сохранённые и после ротации. Если ключ мог утечь, ротации мало — нужна полная смена ключей (раздел «Утечка ключа» ниже).

Код: `backend/app/core/crypto.py` (шифрование, мастер-ключ), `backend/app/core/vault.py` (ключи визовиков, перешифровка).

### Новый ключ

```bash
uv run python -m app.cli generate-master-key
```

Значение (32 случайных байта в base64) кладётся в переменную `VAULT_MASTER_KEY`: на Railway — в Variables сервиса, локально — в `backend/.env`. У production и staging разные ключи. Ключ хранится ещё и вне Railway (менеджер паролей владельца): если он потерян, зашифрованные данные не восстановить.

### Ротация

Когда: по расписанию, раз в год. При подозрении на утечку ключа и при уходе человека, который видел переменные Railway, — полная смена ключей (раздел «Утечка ключа»): у кого был доступ к переменным, у того мог быть и доступ к базе.

1. Сгенерировать новый ключ (`generate-master-key`).
2. В переменных сервиса: `VAULT_MASTER_KEY_PREVIOUS` = старый ключ, `VAULT_MASTER_KEY` = новый. Задеплоить. Пока задан предыдущий ключ, приложение читает секреты обоими ключами, а новые шифрует новым — работа не прерывается.
3. Перешифровать всё новым ключом:
   ```bash
   uv run python -m app.cli rotate-master-key   # «Re-encrypted N secrets»
   ```
   Команда безопасна для повторного запуска: второй запуск перешифровывает 0.
4. Удалить `VAULT_MASTER_KEY_PREVIOUS`, задеплоить, проверить, что вход с двухфакторным кодом и показ пароля из сейфа работают.
5. Старый ключ уничтожить. Бэкапы, сделанные до ротации, по-прежнему открываются только старым ключом — храните его, пока не истекут эти бэкапы.

### Утечка ключа: полная смена ключей

Когда: мастер-ключ мог попасть к постороннему, особенно вместе с копией базы или бэкапом. Команда `rekey-after-leak` (`backend/app/cli.py`, `backend/app/core/vault.py`) делает три вещи:

- даёт каждому визовику новый ключ данных и шифрует им заново пароли сейфа и все файлы в хранилище (договоры, согласия, шаблоны);
- выключает двухфакторный вход у всех пользователей и удаляет их коды восстановления: секреты приложений-аутентификаторов были зашифрованы утёкшим ключом;
- завершает все сессии, в том числе входы, которые ждут код.

После неё ни старый мастер-ключ, ни копия базы до смены не открывают того, что лежит в базе и хранилище. Данные, которые уже были у постороннего в копии, остаются у него: смена защищает то, что будет сохранено потом, и нынешние файлы от будущей утечки хранилища.

**До запуска.** Предупредите визовиков: их выкинет из системы, двухфакторный вход придётся включить заново, и пока идёт смена, работать не нужно. Пока шифруются файлы кабинета, кабинет ждёт: его запросы через 10 секунд заканчиваются ошибкой. У пилота это секунды или минуты, в худшем случае (10 ГБ файлов у кабинета) — десятки минут: каждый файл скачивается и загружается заново один раз. Файл, загруженный в момент смены, может остаться под старым ключом и перестать открываться.

1. Сгенерировать новый мастер-ключ (`generate-master-key`) и новый `SECRET_KEY` (раздел «Коды восстановления»): все коды восстановления команда всё равно удалит, так что ничего не сломается.
2. В переменных сервиса: `VAULT_MASTER_KEY_PREVIOUS` = утёкший ключ, `VAULT_MASTER_KEY` = новый, `SECRET_KEY` = новый. Заодно смените другие секреты, которые видел этот человек: пароль базы, ключи `S3_*`, пароль SMTP. Задеплоить.
3. Запустить смену:
   ```bash
   uv run python -m app.cli rekey-after-leak   # попросит набрать REKEY; --yes — без вопроса
   ```
   В конце команда пишет, сколько кабинетов, паролей и файлов перешифровано и у скольких пользователей выключен двухфакторный вход. Без `VAULT_MASTER_KEY_PREVIOUS` или с тем же ключом в обеих переменных она отказывается работать.
4. Если команда остановилась (сбой хранилища, кабинет занят импортом дольше 10 секунд), запустите её снова с теми же переменными. Каждый кабинет меняется в своей транзакции: недоделанный остаётся со старым ключом, а файлы, которые уже успели перешифровать, команда узнаёт и не трогает. До повторного запуска эти файлы в недоделанном кабинете не открываются, так что не откладывайте его. Кабинеты, прошедшие смену, получат новый ключ ещё раз — это лишняя работа, но не вред. Двухфакторный вход тоже сбрасывается снова: кто успел его включить между запусками, включит ещё раз.
   Сообщение «a file opens with neither key (contact_documents …)» значит, что файл в хранилище повреждён или не от этой строки — он не открывался и до смены. Этот кабинет остался со старым ключом. Попросите визовика удалить файл в карточке клиента (и загрузить заново, если файл у него есть), потом запустите команду снова.
5. Удалить `VAULT_MASTER_KEY_PREVIOUS`, задеплоить, проверить: вход по паролю (двухфакторный вход выключен), показ пароля из сейфа, скачивание договора и шаблона.
6. Попросить всех включить двухфакторный вход заново в «Настройках». Если утекла копия базы, попросите ещё сменить пароли: хеши паролей из копии можно перебирать.
7. Старый ключ уничтожить, когда истекут бэкапы, сделанные до смены: они открываются только им.
