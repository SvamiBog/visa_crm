# VisaCRM — контекст для Claude Code

CRM для визовика (специалиста, который ведёт клиентов «под ключ»: визы в ЕС, UK и другие страны). Сначала ею пользуется один визовик из Беларуси, затем, с этапа 3, она открывается другим визовикам как SaaS по подписке (оплаты отмечает админ); оплата за каждый слот, полученный модулем слотов, — отдельно от подписки и только с этапа 7. Этап 0 (фундамент) готов, этап 1 (ведение клиентов) сделан, идёт пилот с визовиком (первые правки по её замечаниям — 20.11.2026); идёт **этап 2 (документы)**, сначала задачи без материалов визовика.

## Команды

```bash
docker compose up -d                     # локальный Postgres 18 и Mailpit (письма — http://localhost:8025)
cd backend && cp .env.example .env
uv sync                                  # зависимости (создаст uv.lock — коммитить)
uv run alembic upgrade head              # миграции
uv run uvicorn app.main:app --reload     # API на :8000, документация /api/docs
uv run pytest                            # тесты (нужен Postgres: создают базу visacrm_test, адрес — TEST_DATABASE_URL)
uv run ruff check . && uv run ruff format .
alembic revision --autogenerate -m "..."  # новая миграция (через uv run)
uv run python -m app.cli create-admin EMAIL  # первый админ платформы (другие команды — docs/operations.md)
uv run python -m app.cli seed-demo        # демо-данные стенда (ENV=local/staging, DEMO_PASSWORD; DEMO_TOTP_SECRET — по желанию)

cd frontend && npm install               # создаст package-lock.json — коммитить
npm run dev                              # UI на :5173, /api проксируется на :8000
npm run build                            # проверка типов + сборка в frontend/dist
DEMO_PASSWORD=… npx playwright test      # браузерные тесты форм (frontend/e2e): нужен API на :8000 со сборкой и seed-demo

graphify update .                        # граф кода в graphify-out/: локально, без ИИ, ~30 с (см. «graphify» в конце)
```

## Архитектура и правила

- **Один веб-сервис.** FastAPI отдаёт `/api/*` и собранный фронтенд из `frontend/dist` с того же домена — так cookie-сессии работают без CORS. Деплой: `Dockerfile`, Railway, регион EU West (Амстердам); путь к Dockerfile, healthcheck и перезапуск — в настройках каждого сервиса в Railway (docs/deploy.md, шаг 3), `railway.json` нет. На этапе 1 есть ещё только Postgres и cron-сервис (курсы валют, бэкап).
- **Мультиарендность с первого дня.** Визовик = арендатор (`tenant`). Каждая бизнес-таблица несёт `tenant_id`, доступ ограничен и в коде, и Row-Level Security в Postgres. Как это работает: в начале каждой транзакции сессия переключается на роль `visacrm_app` (`SET LOCAL ROLE`, у роли нет обхода RLS) и выставляет `app.tenant_id` (или `app.system = on` для входа и админки) — см. `app/core/db.py`: `scope_to_tenant` / `scope_to_system`. Сессия без области видимости не видит ни одной строки. Сессии входа и коды восстановления видны кабинету только для его собственных пользователей (миграция 0007) — так визовик управляет своими сотрудниками, не выходя из своей области. Новая бизнес-таблица в миграции: колонка `tenant_id`, `ENABLE ROW LEVEL SECURITY` и политика `tenant_isolation` (образец — `enable_tenant_rls` в миграции 0001) плюс тест изоляции. Дочерняя строка ссылается на родителя визовика составным ключом `(parent_id, tenant_id)` (образец — `_tenant_fk` в `app/models/dictionaries.py`), чтобы нельзя было сослаться на чужую запись. Общие для всех данные (страны и операторы визовых центров, `app/models/reference.py`) — без `tenant_id`: читают все области, пишет только системная (политики `enable_shared_rls` в миграции 0009), правит только админ. Так же устроены тарифы подписки (`tariffs`). Оплаты подписки (`subscription_payments`) визовик видит в своей области, но записывать их может только системная область: на таблице стоит ограничивающая политика (миграция 0036). Направления визовика — правила «страна визы × страна подачи» и их города (`country_rules`, `visa_centers`) — его собственные данные (миграция 0034). Сотрудник визовика видит только выданные ему кейсы (`employee_cases`), их группы подачи, их клиентов и то, что завёл сам: его сессия выставляет `app.employee_id`, а на таблицах с данными клиента стоит ограничивающая политика `employee_scope` (миграция 0031). Новая таблица с `contact_id` или `case_id` — ещё и `employee_scope` (проверяет `test_every_table_of_a_client_or_case_is_under_the_employee_scope`). Поле, где записан аккаунт-автор строки, ссылается на `users` составным ключом `(колонка, tenant_id)` (`account_fk` в `app/models/user.py`); новая SECURITY DEFINER-функция — `REVOKE EXECUTE … FROM PUBLIC` и `GRANT … TO visacrm_app`; модули, подписку и блокировку кабинета меняет только системная область (триггер `tenant_changes_allowed`, миграция 0043). Это проверяют тесты `tests/test_db_policies.py`.
- **Роли:** `admin` (владелец платформы, админ-панель), `specialist` (визовик, все рабочие инструменты, без админских), `employee` (сотрудник визовика, только выданные модули и кейсы). Аккаунт визовика создаёт админ с временным паролем; флаг `must_change_password` пускает только на смену пароля. 2FA (TOTP) — по желанию для всех ролей: включается и выключается в «Настройках» (`app/core/two_factor.py`); если включена, при входе нужен код. Доступ в API — зависимости из `app/api/deps.py`: `current_user` (пускает только после смены временного пароля), `require_admin`, `TenantSession` (сессия БД в области визовика), `SystemSession` (вход и админка). Эндпоинты модуля закрываются `Depends(require_module("<ключ>"))` (ключи — `app/core/modules.py`). У сотрудника — дневные лимиты на открытые карточки и кейсы и показанные пароли (`app/core/employee_limits.py`: `watch` до выдачи данных в каждом обработчике, который отдаёт данные карточки, — и в правке, файлах, шаблонах, логинах сейфа; сверх лимита — 429 и сигнал визовику). Ошибки API — коды в `detail` (`invalid_credentials`, …), тексты к ним — `errors.*` в локалях.
- **Деньги.** Только `Decimal` / `NUMERIC(14,2)`, никаких float. Платёж хранит сумму, валюту, курс и сумму в базовой валюте визовика (сейчас BYN). Курс — последний курс Нацбанка РБ (api.nbrb.by), который есть на сайте, для платежа любой даты, редактируемый: сайт сам скачивает курсы при запуске и каждые 3 часа, запросы к банку не ходят. Формулы прибыли, остатка, партнёрской выплаты и налога — в одном модуле с юнит-тестами (`app/core/finance.py`, см. clients-module.md → «Финансы»); курсы Нацбанка — `app/core/rates.py`, хранятся в общей таблице `exchange_rates`. Округление до копеек — `finance.money()` (половина вверх). Расчёты с регистраторами — `app/core/registrar_ledger.py`: баланс в валюте регистратора, талон берётся из финансов кейса.
- **Сейф паролей.** Пароли клиентов шифруются AES-GCM ключом визовика, который сам зашифрован `VAULT_MASTER_KEY` (`app/core/crypto.py`, `app/core/vault.py`: `get_tenant_key`, `encrypt_for_tenant`; ротация — docs/operations.md). Расшифровка только по явному действию, каждый показ пишется в журнал.
- **Журнал действий** — неизменяемый (только INSERT, триггер запрещает UPDATE/DELETE/TRUNCATE): кто, когда, что открыл или изменил. Писать через `app.core.audit.record(session, AuditAction.…, actor=…)` в той же транзакции, что и само действие; новое событие — значение в `AuditAction` и подпись `audit.action.*` в локалях. В `details` — только идентификаторы и короткие технические факты, без данных клиентов.
- **Персональные данные.** Сканы паспортов по умолчанию не храним (они остаются в Telegram у визовика). Храним согласие и договор (дата + файл в S3-хранилище в ЕС): файл до отправки шифруется ключом визовика (`app/core/documents.py`), хранилище — любое S3-совместимое по переменным `S3_*` (`app/core/storage.py`), отдаётся только на скачивание, каждое скачивание — в журнал. Никаких персональных данных в логах, URL и сообщениях об ошибках. Отчёты об ошибках в Sentry (только при `SENTRY_DSN`) собираются из белого списка полей `app/core/error_reports.py`: новое поле уходит, только если добавить его туда вместе с тестом.
- **Темы.** Четыре стиля из docs/prototype/Styles.dc.html: `blue` (A, по умолчанию), `dark`, `warm`, `minimal`; пользователь выбирает в «Настройках». Никаких цветов и шрифтов в компонентах — только переменные темы (`--c-*`, `--font-*`, `--radius-*`) из `frontend/src/styles.css`.
- **i18n.** Ни одной строки интерфейса в коде — только ключи `t("...")` в `frontend/src/locales/{ru,en}.json`. Русский — основной, английский должен быть полным.
- **Время.** В базе — UTC (`timestamptz`), даты без времени — `date`. Отображение — в часовом поясе визовика (по умолчанию Europe/Minsk).
- **Справочники вместо хардкода.** Страны, правила записи (лист ожидания / заявка с окном / прямой слот / посольство, окно в днях, оператор ВЦ, тип идентификатора, приём апелляций), цели, каналы, регистраторы, партнёры, предоплаты, налоги — всё данные, а не константы.
- **Напоминания на этапе 1 — внутри CRM** (вычисляемый список «Требует внимания»: правила и сроки — `app/core/reminders.py`, API — `app/api/reminders.py`). Бот клиента в Telegram запланирован задачей 2.12 (docs/decisions.md → «Подписание договора, страница группы и бот клиента»); других ботов, онлайн-оплат, модуля слотов и мобильного приложения нет — не начинайте их без запроса. Подписка визовиков (3.8) есть: оплаты админ отмечает вручную.

## Как работать

- Порядок работы — docs/process.md. Сессия обсуждения кода не пишет и заканчивается `/handoff`: пункты бэклога с критериями готовности. Сессия разработки — одна задача в своём worktree, `/deliver X.Y`: план, макет экрана, код через тесты, проверки команды. Пункт без критериев или с открытым вопросом в разработку не берём, а возвращаем в обсуждение. Ветку с кодом нельзя отправить, пока каждую затронутую область (код, БД, экраны, тексты, безопасность, уведомления клиентам) не принял её агент; это держит хук `review-gate.cjs`. Пункт вливается одним коммитом (squash) только после проверки на стенде своего PR и «да» владельца; новая функция — за своим флагом по образцу `CLIENT_PORTAL`: на стендах включена, в production выключена, пока владелец не включит (docs/process.md → «Тестовый сервер и флаги»).
- Юридические вопросы (персональные данные, согласия, уведомления, договор, подпись, передача данных третьим) — агенту `legal-advisor`, не решайте их сами. Сложным вопросам — более мощная модель и выше уровень размышления: Fable 5.2 с `xhigh`, юридическим и необратимым — с `max`. Субагенту — `model: "fable"` и `effort` при вызове, сессии разработки — через `set_session_model` и `set_session_effort` (docs/process.md → «Модель и уровень размышления»). Это прямое указание владельца для всех сессий.
- Берите следующую задачу из docs/backlog.md; одна задача — одна ветка и PR, в PR ссылка на пункт бэклога. После мержа отметьте пункт в docs/backlog.md, docs/roadmap.md и на странице «Дорожная карта VisaCRM» (статус и заметка на странице — те же, что в файле). «На проверке» — код влит, но осталась проверка в production; «Готово» — только когда она пройдена.
- Сначала тест на бизнес-правило (особенно деньги, сроки, права доступа), потом код.
- Схема БД меняется только миграциями Alembic; миграции не редактируем после мержа.
- Секреты — только в переменных окружения Railway и локальном `.env`, никогда в репозитории.
- Решение, которое меняет продукт, записывайте в docs/decisions.md; если вопрос не решён — добавьте в docs/open-questions.md и спросите, а не угадывайте.
- Документация и общение — на русском; код, имена, комментарии и коммиты — на английском.

## Claude Code

- **Правила** — `.claude/rules/ecc/`, на английском: `common/` загружаются всегда, `python/` и `typescript/` — при работе с файлами бэкенда и фронтенда. Где правило расходится с этим файлом или документацией, прав этот файл.
- **Хуки** (`.claude/settings.json`, `.claude/hooks/`, нужен Node): правка `.py` в `backend/` форматируется `ruff format`; блокируются правка миграции, которая уже есть в `origin/main`, и новая таблица в миграции без RLS (`enable_tenant_rls` / `enable_shared_rls`); перед поиском и чтением файлов подсказывает граф кода (см. «graphify»); в облачной сессии при старте запускается Postgres; `git push`, `gh pr create` и создание PR через GitHub блокируются, пока затронутые веткой области не приняты их агентами (`review-gate.cjs`, docs/process.md → «Проверки перед PR»). Записи через Bash хуки не видят.
- **Команды, агенты, скиллы** — адаптированные копии ECC с префиксом `ecc-` (список и лицензия — `.claude/ECC-NOTICE.md`). Задача: `/ecc-plan` → подтверждение → скилл `ecc-tdd-workflow` → `/ecc-code-review`; по просьбе — агенты `ecc-planner`, `ecc-tdd-guide`, `ecc-code-reviewer`. Ревью одной стороны: `/ecc-python-review`, `/ecc-fastapi-review`, `/ecc-react-review`, агенты `ecc-database-reviewer` и `ecc-security-reviewer`. Аудит безопасности всего кода по областям (изоляция визовиков, доступ, вход, сейф, файлы, разбор загрузок, персональные данные, целостность, сохранность, веб, инфраструктура) — агент `ecc-vulnerability-hunter`: только читает код, находки доказывает тестом, стенды и production не трогает. Проверка запущенного сайта и базы по тем же областям — агент `ecc-site-security-tester`: поднимает локальный стенд с демо-данными (или берёт стенд PR) и шлёт настоящие запросы; общий `staging` — только чтение, `production` — только пассивно (заголовки, TLS, `/api/health`), без входа и перебора; без DoS. Улучшения интерфейса для визовика (понятные названия разделов, меньше лишнего на экране — прятать редкое и открывать по месту, группировка) — агент `ecc-ux-reviewer`: по умолчанию смотрит запущенное приложение со скриншотами и возвращает список правок с файлами и ключами локалей, по принятому списку сам правит фронтенд в ветке с i18n и браузерными тестами (коммит и PR — по «да»). Скиллы `ecc-database-migrations`, `ecc-i18n-sync`, `ecc-e2e-testing`, `ecc-context-budget` (вес правил и компонентов в контексте). Заметки о сессии — `/ecc-save-session` и `/ecc-resume-session` в `.claude/session-data/` (не в git).
- **Свой агент проекта** (не из ECC): `specialist-simulator` — играет визовика на локальном стенде или стенде PR: неделя работы с вымышленными клиентами через интерфейс (лид и консультация, семья, очередь и Франция, сейф, платежи в валютах, брони, документы, результат, повторный клиент, сотрудник), сверяет суммы и напоминания со спецификацией и возвращает по-русски список проблем в работе с клиентами по уровням. Файлы проекта не меняет. `copy-editor` — редактор текстов сайта: подсказки, пустые состояния, подтверждения, ошибки и письма, которые звучат как написанные машиной (цепочки тире и двоеточий, обрывки без глагола, канцелярит), переписывает простым русским языком, английский держит в шаг; смысл, числа, подстановки и названия разделов не трогает. Правит локали, коммит — по «да». Свой скилл `buttons-and-spacing` — кнопки и отступы экрана: три вида кнопок из переменных темы (главная, обычная с заливкой, опасная красная), зазор в каждом ряду кнопок, шкала отступов; снимает экран на 390 и 1280px во всех темах (`screens.cjs` рядом со скиллом), правит `styles.css` и доказывает правку тестом `frontend/e2e/buttons.spec.ts`.
- **Команда задачи** (свои, docs/process.md): `/handoff` в сессии обсуждения — агент `product-analyst` сверяет идею с продуктом и кодом и режет её на пункты бэклога; `/deliver X.Y` в сессии разработки ведёт задачу от плана до PR. Агент `screen-designer` рисует экран до кода: макет `docs/prototype/<область>-<что>.html` из стилей приложения, все состояния, 390 и 1280px. Агент `design-qa` принимает каждое изменение экранов: собирает ветку, меряет экраны и формы скиллом `ui-audit` (`audit.cjs`: элементы одного вида разного размера, слипшиеся кнопки, выход за экран, шрифты вне шкалы; 390 и 1280px, четыре темы), смотрит снимки и возвращает «ПРИНЯТО» или «НА ДОРАБОТКУ». Агент `legal-advisor` — юрист проекта на Fable 5.2 с максимальным уровнем размышления: GDPR и право Польши (не Беларуси), статьи и первоисточники, риски и варианты, черновики уведомлений и договора, что подтвердить у польского юриста до production; принимает ветки, которые меняют уведомления и согласия клиентов (область `legal`).
- **Облачная сессия** плагинов не загружает и видит только файлы репозитория. Окружение готовит `.claude/cloud-setup.sh` (вставляется в настройки окружения на claude.ai): Node 22, зависимости бэкенда и фронтенда и локальный Postgres вместо `docker compose`; скрипт всегда выходит с кодом 0. Postgres в каждой сессии запускает хук `.claude/hooks/cloud-session.cjs`.

## graphify

Граф кода и документов проекта — `graphify-out/graph.json`: функции, классы, импорты и вызовы бэкенда и фронтенда, разделы `docs/*.md`. Он не в git, у каждой рабочей копии свой. Строит и обновляет его `graphify update .`: tree-sitter разбирает файлы локально, без ИИ и сети, около 30 секунд. Полная сборка `/graphify .` (скилл `.claude/skills/graphify/`, вариант для Windows) ещё и читает документы субагентами — это токены (на весь проект около 2 млн), запускайте только по просьбе. После неё документы в графе — понятия и решения со связями с кодом, а заголовков разделов нет. Что не входит в граф, перечислено в `.graphifyignore` (там документация самого graphify). graphify ставится один раз на машину: `uv tool install "graphifyy[mcp]"` (пакет `graphifyy` на PyPI, Apache-2.0, github.com/Graphify-Labs/graphify; без `[mcp]` не работает `graphify explain`).

Правила:
- Если `graphify-out/graph.json` есть, на вопрос о коде сначала `graphify query "<вопрос>"`, потом grep, поиск и чтение исходников; это же правило пишите в промт каждого субагента, который исследует код. Сырые файлы читайте только там, где граф или прошлое чтение уже нашли нужные строки. Связь двух мест — `graphify path "<A>" "<B>"`, одно понятие — `graphify explain "<понятие>"`, раздел документа по заголовку — `graphify section "<заголовок>"` (тогда .md открывать не нужно). `section` работает, только если граф построен `graphify update .`; после полной сборки он ответит «not a Markdown heading» — тогда читайте строки .md, на которые указал граф. Имя, которое есть в нескольких файлах, уточняйте как `путь::символ`. Про код спрашивайте по-английски, про документы можно по-русски.
- `graphify-out/GRAPH_REPORT.md` — только для обзора всей архитектуры или когда query, path и explain не нашли нужного.
- После правки кода — `graphify update .`. Документы в графе полной сборки эта команда не трогает: их обновляет `/graphify --update`, он перечитывает только изменённые файлы. В рабочей копии без графа правила не действуют; нужен граф — постройте его `graphify update .`.
- Хук `.claude/hooks/graphify-hook-guard.cjs` перед Bash, Grep, Read и Glob подсказывает, что уже есть в графе, и говорит, когда граф устарел (не больше пяти подсказок за сессию). Без графа или без graphify он молчит.
